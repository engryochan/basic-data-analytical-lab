第一章、简介

1.1 研究背景与目的

本报告是”商君风控体系”项目的数据篇，目标是为荷官与玩家风控（真人视讯博彩场景）建立一套从原始数据到可执行复核名单的完整、可追溯链路——每一个结论都能回溯到具体的SQL/R代码与实测数字，不接受任何未经验证的假设。

具体要解决三条业务方提出的风控需求：策略性投注识别（利用牌靴统计特性的算牌行为）、团伙同桌识别（疑似合谋洗流水的关联账号）、用户与荷官作弊识别（荷官与特定玩家的异常获利关联）。第三条因真实数据存在缺口，目前暂缓（详见第二章第八节），前两条已完整跑通并产出可执行名单（详见第七、八章）。

1.2 ⚠️ 关键前提：本报告使用的是局部数据，不是全局数据

这是理解本报告全部结论前必须先知道的一件事，放在全文最前面，而不是埋在后面某个章节里。

本报告随交付包附带的数据库/文件夹里，每张原始表约10万行，这是从生产环境ods_a168_*系列表抽样导出的局部数据，不是生产环境的全量数据。生产环境（ods_mariadb_2b.ods_a168_bet01）在真实StarRocks在线库上实测的全量行数是173,529,760行（第二部第五章有完整实测记录），是这份10万行局部数据的约1,735倍。

这意味着什么，讲清楚，不回避：

  1. 本报告第一部～第二部（数据审核、字段验证、盈亏字段排查等）用10万行局部数据即可完成，因为这些是”验证字段含义/表结构/数据质量”这类工作，局部数据规模足够；
  2. 但第七、八章”团伙同桌59,833组配对”“策略性投注4,929人候选”“24人双重命中名单”这几个具体数字，是在StarRocks全局数据（1.74亿行）上直接查询产出的，不是从随附的10万行局部数据里跑出来的——如果您在自己电脑上用随附的10万行局部数据重新跑第七章的代码，得到的候选人数会远小于报告里写的数字，这不是代码错了，是局部数据规模本身的差距决定的；
  3. 报告里所有涉及”全量/在线库实测”的数字，都会在正文明确标注数据来源（局部数据 vs StarRocks在线全量），不会把两种来源的数字混着讲。

在风控系统的实际运转中，“多久算一次”与”算出来后怎么处置”是紧密绑定的。风控的核心原则是：用最小的计算成本，在黑产资金提现出网前完成拦截，同时最大程度避免误伤正常玩家。 下面为你详细拆解这 6 项监控计算项目、设计初衷及其触发处置动作背后的商业逻辑：

1. 同 IP 高频聚集检测

  • 计算频率：准实时（每 5~15 分钟）
  • 回溯窗口：过去 24 小时
  • 计算逻辑：统计同一个 IP 下绑定的独立 player_id 数量。当出现  ≥ 5 个账号且流水/下注笔数达到门槛时触发。
为什么是这个频率？

工作室批量切号、脚本自动注册下注是高频爆发式的。如果等到第二天再算，黑产可能已经完成了注册、下注、刷完优惠券全流程。5~15 分钟的微批计算能将危害控制在萌芽期。

处置动作与底层逻辑：
  • 动作：将热点 IP 写入 Redis 集合，同步触发钉钉/Telegram 告警。
  • 底层逻辑：
    1. Redis 热点拦截：网关或注册/登录 API 读取 Redis，对该 IP 实施动态防护加码（如强制弹出拼图验证码、二次人脸识别，或直接限制该 IP 下的新账号注册）。
    2. 告警人工复核：给风控值班人员发送预警，及时发现机房/代理服务器节点。

2. 高赔率副盘压秒偷窥

  • 计算频率：准实时（每 15~30 分钟）
  • 回溯窗口：过去 12 小时
  • 计算逻辑：筛选开局 15 秒后下注高赔率盘口（Super6、Tie 等）的注单，计算其压秒占比（ > 50%）与压秒注单 ROI（ ≥ 80%）。
为什么是这个频率？

高赔率盘口的赔率高达 1:8 到 1:12，黑产利用视频延时“窥牌压秒”在短时间内能卷走大额资金。15~30 分钟计算一次，确保在黑产点击“提现”按钮前将账号标记。

处置动作与底层逻辑：
  • 动作：自动将账号标记为 HOLD_PAYOUT（挂起提现）。
  • 底层逻辑：
    • 为什么不直接封号？ 极少数网络极差的真实玩家也可能偶然出现压秒，直接封号会导致剧烈客诉。
    • 挂起提现（Hold Payout）：允许玩家继续下注/游玩，但一旦发起提现申请，系统自动进入“人工审核流程”。风控人员可调取该玩家下注时刻与荷官发牌的视频帧进行对齐（Frame Alignment），确认偷窥无误后再做永久封号处理。只要钱没提走，平台就没有损失。

3. 刷水洗码 / 低盈亏比

  • 计算频率：近实时（每 1 小时）
  • 回溯窗口：过去 3 天
  • 计算逻辑：统计流水  ≥ 5 万、盈亏边际率  ≤ 0.5% 且算上平台返水后团队净收益  > 0 的账号。
为什么是这个频率？

刷水团队不是靠一两局游戏获利，而是依靠长时间、大流水累积返水。1 小时的频率足以捕获其行为趋势，且不会消耗过多计算资源。

处置动作与底层逻辑：
  • 动作：冻结返水/佣金发放（LIMIT_REBATE）。
  • 底层逻辑：
    • 刷水黑产的核心收益来源就是平台发放的返水（Rebate）。只要在每周/每日的返水结算点之前，将其返水权限冻结或归零，其攻击的 ROI 就直接变成了负数。黑产发现无法拿到返水后会自然离场，平台无需与黑产陷入繁琐的注单争议中。

4. 庄闲精准对打套利

  • 计算频率：离线批处理（每日 T+1 / 凌晨跑）
  • 回溯窗口：过去 7~30 天
  • 计算逻辑：跨账号配对，查找同一桌、同一靴、同一局下注相反方向，且累积对打  ≥ 20 局、损耗率  < 2.5% 的账号对。
为什么是这个频率？

庄闲对打需要足够多的样本量（ ≥ 20 局）才能在统计学上剔除“巧合撞车”。在大数据量下进行全量两两 Join 匹配属于高消耗计算，放在夜间闲时做 T+1 离线计算最为高效。

处置动作与底层逻辑：
  • 动作：批量挂起提现，并追溯扣除上级代理佣金。
  • 底层逻辑：
    • 对打套利往往伴随着代理自导自演（代理注册 A、B 两个小号对打刷流水，吃平台 40% 的负盈利佣金或流水返佣）。T+1 计算不仅能锁定下注账号，还能通过代理树图，将该团队产生的所有违规流水从代理的月度佣金切片中全额扣除（Clawback）。

5. GraphX 关联图图谱

  • 计算频率：离线（每周 / 每日深夜）
  • 回溯窗口：过去 30 天
  • 计算逻辑：以账号为节点，共享的 IP、设备指纹、提现银行卡为边，运行连通分量算法（Connected Components），识别独立节点数  ≥ 5 的大连通块。
为什么是这个频率？

图算法（Graph Mining）涉及大规模矩阵运算与节点迭代，数据时间跨度越长（30 天），拉出的黑产网络越完整。不需要高频运行，每周或每日深夜跑一次即可。

处置动作与底层逻辑：

  • 动作：生成团伙 ID（Cluster ID），打上连通标签。
  • 底层逻辑：
    • 一网打尽与“株连”机制：黑产团伙往往用“养号”策略，一部分号做测试，一部分号做主攻击。当团伙中某一个号（如 Account A）因压秒被确诊封禁时，系统通过 Cluster ID 可以瞬间锁定同一社群内的另外 8 个潜伏账号，直接对其采取一键协同风控，防止其换号继续攻击。

6. 孤立森林无监督计算

  • 计算频率：离线（每周二次 / 每周）
  • 回溯窗口：过去 14 天
  • 计算逻辑：提取多维行为特征向量，运行 Isolation Forest，输出异常得分（outlier_score），提取 Top 1% 离群玩家。
为什么是这个频率？

孤立森林的定位是探索未知的黑产变种（新型软件、未知脚本）。由于是无监督学习，它发现的是“长得怪异”的人，需要留出时间给人工进行审核沉淀。

处置动作与底层逻辑：
  • 动作：推送至影子复核队列（Shadow Review），由风控审核员进行伪标签打标。
  • 底层逻辑：
    • 防误伤安全阀：由于没有已知标签，绝对不能直接自动化封号。孤立森林的结果只作为“人工排查的线索放大镜”。风控人员抽检确诊后，打上 Label = 1（黑产）或 Label = 0（正常高 VIP 玩家），这些伪标签将反哺并优化下一代风控规则。

总结：风控处置动作的阶梯式控制

系统对账号的处置遵循“由软到硬”的阶梯式防控：

动态验证码/KYC (软) → 限制返水/佣金 (中) → 挂起提现 Hold Payout (硬) → 永久封号/拉黑 (终)

读取列名映射 <- function(glimpse文件路径) {
  gd <- fread(glimpse文件路径, encoding = "UTF-8")
  stopifnot(all(c("column_name", "column_type", "comment") %in% names(gd)))

  }

分类函数 <- function(name) {
  n <- tolower(name)
  if (grepl("redpacket", n)) return("红包活动类")
  if (grepl("agent|age_login|age_sub_login|subagent|agents_loginpass", n)) return("代理体系类")
  if (grepl("partner", n)) return("三方合作类")
  if (grepl("^ods_a168_bet|betchange|ban_bet|realtimebet|log_realtimebet|bet_limit", n)) return("投注行为类")
  if (grepl("in_out_m|wallet|payment|jackpot|log_age_cash_change|aggregate_transaction", n)) return("资金流水类")
  if (grepl("game_|category|shuffle|symbol|odds_default|play_set|tablelimit", n)) return("游戏系统配置类")
  if (grepl("iphistory|ipblacklist|alert_ip|risklist|white_list|close_tip_list|passiplist|temp_id_list", n)) return("网络设备与风控名单类")
  if (grepl("dailyreport|aggregate_setting|aggregate_token|func_counter", n)) return("报表汇总类")
  if (grepl("smr_log|game_log|alarmmessage|alertmessage|change_log|keyserver|opengame_log|realtimelog|stream|sync_checkpoint", n)) return("系统技术日志类")
  if (grepl("permission|roles|employee|emp_login|control", n)) return("权限与员工管理类")
  if (grepl("member", n)) return("会员身份与账户类")
  return("系统配置/其它类")
}

7.4 模型融合（Stacking）：一个诚实的负面/中性结果

  2. 这不代表贝叶斯/逻辑回归这条路没有价值——它的价值不在”分类精度比XGBoost高”，而在能输出带不确定性区间的概率估计、能做层级结构建模(承认同一个人参与的配对不独立)、以及在样本量较小或需要严谨统计推断的子场景里更可靠，这跟”哪个模型分类打分打得准”是两个不同维度的价值，不能用一个AUC数字就否定贝叶斯方法。
  3. 对”打分系统架构设计”(第二部第五章5.2节)的直接指导：现阶段结论是评分层直接用XGBoost单独打分即可，不需要再叠加复杂的Stacking框架——复杂度增加了，但效果没有对应提升，不符合”用最小代价达到目标”这个工程原则。如果未来纳入更多元、更异质的数据源(比如真正补齐盈亏字段之后)，各路信号之间的互补性可能会变强，届时应该重新评估Stacking是否有价值，不是一次性结论。
