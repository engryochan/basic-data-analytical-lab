# 同桌对打风控分析报告

## 一、技术摘要

本分析用于识别真人百家乐中长期固定同桌、且经常采用庄闲相反方向下注的玩家组合。

基于现有历史数据，已得到以下主要结论：

- 全量玩家关系共约 **1.617亿对**，其中 **88.53%** 的玩家对共同同桌不足10局，说明绝大多数关系属于偶然同桌。
- 共同同桌达到100局的玩家对约 **39.37万对，占全部关系约0.24%**，因此 `same_round >= 100` 已是较严格的长期关系过滤条件。
- 在玩家各自至少参与100局、且双方共同同桌至少100局的组合中，同桌率P95为 **19.53%**、P99为 **51.02%**。
- 同一筛选口径下，对打率P95为 **72.33%**、P99为 **96.08%**。
- 建议将“共同同桌局数≥100、同桌率≥20%、对打率≥60%”作为重点审核规则；同桌率≥50%、对打率≥90%可作为极高异常等级。

该规则识别的是异常玩家关系和下注模式，不能单独证明作弊、对刷或资金转移，应作为人工审核线索使用。

## 二、分析范围与数据字段

### 2.1 数据来源

数据表：

```text
ods_a168_bet02
```

百家乐筛选条件：

```sql
bet02 = '101'
```

### 2.2 关键字段

| 字段 | 含义 |
|---|---|
| `bet03` | 场次编号，一般对应一靴牌 |
| `bet04` | 子场次编号，即当前牌靴的局号 |
| `bet05` | 会员ID |
| `bet09` | 下注内容，如 `Banker`、`Player` |
| `bet11` | 汇率 |
| `bet13` | 下注金额 |
| `bet14` | 派彩金额 |
| `validbet` | 有效投注 |
| `bet39` | 桌号 |
| `bet40` | 房间编号 |
| `bet08` | 下注时间 |
| `ip` | 下注IP |

### 2.3 一局百家乐的识别方式

当前分析使用：

```text
bet03 + bet04
```

作为一局百家乐的唯一标识。

如果 `bet03` 并非全平台全局唯一，应将桌号或房间号加入局键，例如：

```text
bet40 + bet39 + bet03 + bet04
```

否则不同桌台恰好出现相同 `bet03 + bet04` 时，可能被错误识别为同桌。

## 三、核心指标定义

### 3.1 玩家总局数

> 玩家总局数表示玩家参与庄或闲主投注的去重百家乐局数。

```text
玩家总局数 = COUNT(玩家参与的唯一局)
```

当前规则先保留总局数不少于100局的玩家：

```sql
HAVING COUNT(*) >= 100
```

该条件用于剔除低活跃玩家，减少小样本下100%同桌率或100%对打率造成的误报。

### 3.2 共同同桌局数

> 共同同桌局数表示两名玩家同时出现在同一场次、同一子场次中的局数。

```text
same_round
= 两名玩家共同参与的唯一百家乐局数
```

需要特别说明：

> 当前 SQL 统计的是“共同同桌局数”，不是原始“同桌订单笔数”。

因为数据已经被整理成“每个玩家、每局一行”，即使某位玩家同一局产生多张订单，最终也只计算为一局。

如果业务规则明确要求“同桌订单数超过100笔”，需要另行定义订单配对口径；团伙关系分析通常更推荐使用去重局数，避免同一局拆单造成虚高。

### 3.3 同桌率

> 同桌率衡量两名玩家是否长期固定一起游戏，反映两名玩家之间的关系强度。

计算公式：

```text
同桌率
= 两人共同同桌局数
  / 两人总局数中的较小值
```

即：

```text
same_table_rate
= same_round
  / MIN(uid1_total_round, uid2_total_round)
```

对应SQL：

```sql
p.same_round * 1.0
/ LEAST(uid1_round, uid2_round)
```

使用较小总局数作为分母，是为了衡量活跃度较低的一方有多少游戏局是在和另一方共同进行。

例如：

```text
玩家A总局数：1,000
玩家B总局数：500
共同同桌局数：300

同桌率 = 300 / 500 = 60%
```

这表示活跃度较低的玩家B有60%的游戏局都与玩家A共同进行。

### 3.4 庄闲对打局数

> 庄闲对打局数表示两名玩家共同同桌时，下注方向一方为Banker、另一方为Player的局数。

以下情况计为对打：

| 玩家A | 玩家B | 是否计为对打 |
|---|---|---|
| Banker | Player | 是 |
| Player | Banker | 是 |
| Banker | Banker | 否 |
| Player | Player | 否 |

### 3.5 对打率

> 对打率衡量两名玩家在共同同桌的游戏局中，庄闲下注方向保持相反的比例。

计算公式：

```text
对打率
= 庄闲相反下注局数
  / 两人共同同桌局数
```

即：

```text
opposite_rate
= opposite_round / same_round
```

对打率的分母是两个人共同玩的局数，不是玩家A或玩家B的历史总局数。

例如：

```text
两人共同同桌：200局
其中庄闲相反：180局

对打率 = 180 / 200 = 90%
```

### 3.6 同桌率与对打率的区别

| 指标 | 同桌率 | 对打率 |
|---|---|---|
| 回答的问题 | 两人是否经常一起玩 | 两人一起玩时是否经常一庄一闲 |
| 分子 | 共同同桌局数 | 庄闲相反下注局数 |
| 分母 | 两人总局数中的较小值 | 两人共同同桌局数 |
| 描述维度 | 玩家关系强度 | 下注行为模式 |
| 主要用途 | 识别固定搭档 | 识别持续对打 |

## 四、共同同桌局数分布

历史玩家关系分布如下：

| 共同同桌局数 | 玩家对数量 | 占全部玩家对比例 |
|---|---:|---:|
| <10 | 143,187,649 | 约88.53% |
| 10–29 | 15,214,455 | 约9.41% |
| 30–49 | 1,961,388 | 约1.21% |
| 50–99 | 992,087 | 约0.61% |
| 100–299 | 346,572 | 约0.21% |
| ≥300 | 47,111 | 约0.03% |
| **合计** | **161,749,262** | **100%** |

主要发现：

1. 绝大多数玩家关系属于低频偶然同桌；
2. 共同同桌不足30局的玩家对约占97.93%；
3. 共同同桌达到100局的玩家对共393,683对；
4. `same_round >= 100` 仅覆盖约0.24%的玩家关系；
5. 共同同桌达到300局的玩家对仅约0.03%，可作为更高关系强度等级。

因此，将共同同桌局数设为100局，可以有效过滤绝大多数随机同桌关系。

## 五、同桌率分布

统计口径：

```text
玩家A总局数 ≥100
玩家B总局数 ≥100
共同同桌局数 ≥100
```

结果如下：

| 分位数 | 同桌率 |
|---|---:|
| P50 | 2.32% |
| P90 | 11.80% |
| P95 | 19.53% |
| P99 | 51.02% |

解读：

- 50%的长期同桌玩家对，同桌率不超过2.32%；
- 同桌率达到约20%，已经进入最高5%左右；
- 同桌率达到约51%，进入最高1%左右；
- 原计划使用30%作为阈值，位于P95与P99之间，适合作为高风险关系阈值。

同桌率风险分层建议：

| 等级 | 同桌率 |
|---|---:|
| 观察 | ≥20%，约P95 |
| 重点审核 | ≥30% |
| 极高异常 | ≥50%，约P99 |

## 六、对打率分布

统计口径与同桌率一致：

```text
玩家A总局数 ≥100
玩家B总局数 ≥100
共同同桌局数 ≥100
```

结果如下：

| 分位数 | 对打率 |
|---|---:|
| P50 | 45.76% |
| P90 | 62.07% |
| P95 | 72.33% |
| P99 | 96.08% |

### 6.1 中位数接近理论随机水平

如果两名玩家只在Banker和Player之间独立选择，并且两种方向概率接近，则两人下注方向相反的理论概率约为50%。

历史P50为45.76%，与理论水平基本接近。略低于50%可能与玩家整体更偏好Banker、同向跟路行为等因素有关。

### 6.2 高分位代表极端持续对打

- 对打率达到62.07%时进入最高10%左右；
- 达到72.33%时进入最高5%左右；
- 达到96.08%时进入最高1%左右。

对打率风险分层建议：

| 等级 | 对打率 |
|---|---:|
| 观察 | ≥62%，约P90 |
| 重点审核 | ≥75%，略高于P95 |
| 极高异常 | ≥90% |
| 极端异常 | ≥96%，约P99 |

## 七、阈值选择建议

### 7.1 推荐重点审核规则

```text
玩家A总局数 ≥100
AND 玩家B总局数 ≥100
AND 共同同桌局数 ≥100
AND 同桌率 ≥30%
AND 对打率 ≥75%
```

选择依据：

- 玩家总局数≥100：排除低活跃玩家；
- 共同同桌局数≥100：仅覆盖约0.24%的玩家关系；
- 同桌率≥30%：高于P95的19.53%，同时不像P99的51.02%那样过度严格；
- 对打率≥75%：略高于P95的72.33%，可以识别持续性庄闲反向下注。

### 7.2 分层规则

| 风险等级 | 共同同桌局数 | 同桌率 | 对打率 | 使用建议 |
|---|---:|---:|---:|---|
| 观察 | ≥100 | ≥20% | ≥62% | 行为观察名单 |
| 重点审核 | ≥100 | ≥30% | ≥75% | 推荐人工审核规则 |
| 极高异常 | ≥300或更高 | ≥50% | ≥90% | 优先调查 |
| 极端关系 | ≥300或更高 | ≥51% | ≥96% | 最高优先级线索 |

### 7.3 `OR` 与 `AND` 的区别

宽口径筛查可以使用：

```sql
same_table_rate >= 0.1953
OR opposite_rate >= 0.6207
```

这会同时纳入：

- 长期固定同桌、但未必经常反向下注的组合；
- 对打率较高、但彼此并非固定搭档的组合。

因此，`OR` 更适合生成较宽的观察池，不适合作为高风险结论。

重点审核更推荐使用：

```sql
same_table_rate >= 0.30
AND opposite_rate >= 0.75
```

这样要求关系强度和对打行为同时异常，误报率通常更低。

## 八、推荐的生产版计算SQL

以下SQL做了三个重要处理：

1. 只分析Banker和Player主投注；
2. 每位玩家、每局只保留一种明确下注方向；
3. 排除同一局同时下注Banker和Player的混合方向记录，避免使用 `MAX(bet09)` 随意选择方向。

```sql
WITH main_bet AS (
    SELECT
        CAST(bet03 AS BIGINT) AS session_id,
        CAST(bet04 AS INT) AS round_id,
        CAST(bet05 AS BIGINT) AS player_id,
        bet09 AS bet_type
    FROM ods_a168_bet02
    WHERE bet02 = '101'
      AND bet09 IN ('Banker', 'Player')
      AND bet03 IS NOT NULL
      AND bet04 IS NOT NULL
      AND bet05 IS NOT NULL
),

round_player AS (
    SELECT
        session_id,
        round_id,
        player_id,
        MIN(bet_type) AS bet_type
    FROM main_bet
    GROUP BY
        session_id,
        round_id,
        player_id
    HAVING COUNT(DISTINCT bet_type) = 1
),

player_round AS (
    SELECT
        player_id,
        COUNT(*) AS total_round
    FROM round_player
    GROUP BY player_id
    HAVING COUNT(*) >= 100
),

eligible_round_player AS (
    SELECT
        r.session_id,
        r.round_id,
        r.player_id,
        r.bet_type
    FROM round_player r
    JOIN player_round p
      ON r.player_id = p.player_id
),

pair_stat AS (
    SELECT
        a.player_id AS uid1,
        b.player_id AS uid2,

        COUNT(*) AS same_round,

        SUM(
            CASE
                WHEN
                    (a.bet_type = 'Banker' AND b.bet_type = 'Player')
                 OR (a.bet_type = 'Player' AND b.bet_type = 'Banker')
                THEN 1
                ELSE 0
            END
        ) AS opposite_round

    FROM eligible_round_player a
    JOIN eligible_round_player b
      ON a.session_id = b.session_id
     AND a.round_id = b.round_id
     AND a.player_id < b.player_id

    GROUP BY
        a.player_id,
        b.player_id
),

pair_result AS (
    SELECT
        p.uid1,
        p.uid2,
        p.same_round,
        p.opposite_round,

        ra.total_round AS uid1_round,
        rb.total_round AS uid2_round,

        p.same_round * 1.0
            / NULLIF(
                LEAST(ra.total_round, rb.total_round),
                0
            ) AS same_table_rate,

        p.opposite_round * 1.0
            / NULLIF(p.same_round, 0) AS opposite_rate

    FROM pair_stat p
    JOIN player_round ra
      ON p.uid1 = ra.player_id
    JOIN player_round rb
      ON p.uid2 = rb.player_id
)

SELECT
    uid1,
    uid2,
    uid1_round,
    uid2_round,
    same_round,
    ROUND(same_table_rate, 4) AS same_table_rate,
    opposite_round,
    ROUND(opposite_rate, 4) AS opposite_rate

FROM pair_result

WHERE same_round >= 100
  AND same_table_rate >= 0.30
  AND opposite_rate >= 0.75

ORDER BY
    same_table_rate DESC,
    opposite_rate DESC,
    same_round DESC;
```

如果 `bet03` 不是全局唯一，应在上述各层中加入 `bet39` 或 `bet40 + bet39`，并将它们加入玩家配对的连接条件。

## 九、分布统计SQL

### 9.1 共同同桌局数分桶

将上一节查询的最后一个 `SELECT` 替换为：

```sql
SELECT
    CASE
        WHEN same_round < 10  THEN '<10'
        WHEN same_round < 30  THEN '10-29'
        WHEN same_round < 50  THEN '30-49'
        WHEN same_round < 100 THEN '50-99'
        WHEN same_round < 300 THEN '100-299'
        ELSE '300+'
    END AS round_group,

GROUP BY
    CASE
        WHEN same_round < 10  THEN '<10'
        WHEN same_round < 30  THEN '10-29'
        WHEN same_round < 50  THEN '30-49'
        WHEN same_round < 100 THEN '50-99'
        WHEN same_round < 300 THEN '100-299'
        ELSE '300+'
    END

ORDER BY
    MIN(same_round);
```

SELECT

## 十、盈利情况分析

### 10.1 两种盈利口径

玩家对命中后可以分析盈利，但必须区分两个口径：

1. **玩家历史总盈利**：统计玩家分析期内全部百家乐订单的盈利；
2. **双方共同同桌期间盈利**：只统计两人共同出现的那些局中的盈利。

历史总盈利可以判断两名玩家整体经营价值，但不能回答他们同桌或对打期间谁获利。

团伙风控更推荐分析共同同桌期间盈利，因为它能回答：

- 两人同桌时是否长期一赢一输；
- 两人对打期间是否出现资金转移特征；
- 两人的共同净盈利是否异常；
- 盈利是否集中在少数特定牌靴、桌号或时段。

### 10.2 汇率口径

根据已确认的业务口径：

```text
统一币种金额 = 原始金额 / bet11
```

玩家盈利：

```sql
(bet14 - bet13) / NULLIF(bet11, 0)
```

有效投注：

```sql
validbet / NULLIF(bet11, 0)
```

ROI：

```text
ROI = 玩家盈利 / 有效投注
```

### 10.3 历史总盈利扩展SQL

在完整的 `pair_result` CTE后增加：

```sql
, profit_stat AS (
    SELECT
        CAST(bet05 AS BIGINT) AS player_id,
        COUNT(*) AS order_cnt,

        SUM(
            CAST(validbet AS DOUBLE)
            / NULLIF(CAST(bet11 AS DOUBLE), 0)
        ) AS valid_bet,

        SUM(
            (
                CAST(bet14 AS DOUBLE)
                - CAST(bet13 AS DOUBLE)
            )
            / NULLIF(CAST(bet11 AS DOUBLE), 0)
        ) AS profit

    FROM ods_a168_bet02
    WHERE bet02 = '101'
      AND bet05 IS NOT NULL
    GROUP BY CAST(bet05 AS BIGINT)
)

SELECT
    r.uid1,
    r.uid2,
    r.same_round,
    ROUND(r.same_table_rate, 4) AS same_table_rate,
    r.opposite_round,
    ROUND(r.opposite_rate, 4) AS opposite_rate,

    p1.order_cnt AS uid1_order_cnt,
    ROUND(p1.valid_bet, 2) AS uid1_valid_bet,
    ROUND(p1.profit, 2) AS uid1_profit,
    ROUND(
        p1.profit / NULLIF(p1.valid_bet, 0),
        4
    ) AS uid1_roi,

    p2.order_cnt AS uid2_order_cnt,
    ROUND(p2.valid_bet, 2) AS uid2_valid_bet,
    ROUND(p2.profit, 2) AS uid2_profit,
    ROUND(
        p2.profit / NULLIF(p2.valid_bet, 0),
        4
    ) AS uid2_roi,

    ROUND(p1.profit + p2.profit, 2) AS pair_total_profit

FROM pair_result r
LEFT JOIN profit_stat p1
  ON r.uid1 = p1.player_id
LEFT JOIN profit_stat p2
  ON r.uid2 = p2.player_id

WHERE r.same_round >= 100
  AND r.same_table_rate >= 0.30
  AND r.opposite_rate >= 0.75

ORDER BY
    r.same_table_rate DESC,
    r.opposite_rate DESC,
    ABS(COALESCE(p1.profit, 0))
      + ABS(COALESCE(p2.profit, 0)) DESC;
```

该SQL输出的是玩家分析期内全部百家乐盈利，不是双方共同同桌局内的盈利。

## 十一、数据质量与方法风险

### 11.1 `MAX(bet09)`可能误分类

原分析SQL使用：

```sql
MAX(bet09) AS bet_type
```

如果一名玩家同一局同时下注Banker和Player，`MAX()`会任意保留排序较大的字符串，导致其被错误标记为单一方向。

建议：

```sql
HAVING COUNT(DISTINCT bet09) = 1
```

只保留下注方向明确的玩家局记录；混合方向下注应单独作为另一种行为分析。

### 11.2 `same_round`不是原始订单数

`round_player`已经聚合到“玩家×局”粒度，因此：

```text
same_round = 共同同桌去重局数
```

不能在报告中称为原始订单笔数。

### 11.3 当前分位数是条件分布

同桌率和对打率分位数是在以下条件下计算的：

```text
双方玩家总局数≥100
共同同桌局数≥100
```

因此，这些P50/P90/P95/P99不能解释为全平台所有玩家对的无条件分布。

### 11.4 时间窗口尚未固定

规则结果会受到分析周期影响。三个月、半年和一年窗口下的总局数与同桌率可能不同。

生产规则应明确：

- 统计窗口，例如滚动30天、90天或180天；
- 业务日期字段；
- 时区和日切时间；
- 是否要求连续多个窗口命中。

### 11.5 不能从相关关系直接推断作弊

高同桌率和高对打率只能证明：

- 两名玩家长期一起游戏；
- 共同游戏时经常一庄一闲。

它不能单独证明两名玩家对刷、洗钱、套利或与荷官串通。

## 十二、上线前复验清单

在将规则用于正式风险处置前，建议完成：

1. 验证 `bet03 + bet04` 的跨桌唯一性；
2. 统计同局同时下注Banker和Player的玩家局占比；
3. 比较使用 `MAX(bet09)` 与排除混合方向后的结果差异；
4. 固定滚动统计窗口并重新计算分位数；
5. 对阈值组合进行参数扫描，比较命中玩家对数量；
6. 分析命中玩家对的共同同桌期间盈利，而非只看历史总盈利；
7. 抽查若干玩家对的原始订单，验证配对、方向和局数是否正确；
8. 使用后续时间段做样本外回测，观察名单稳定性；
9. 统计人工审核确认率和误报率，再决定是否调整阈值。

## 十三、最终结论

现有数据能够支持建立团伙同桌对打的初步筛查规则：

```text
双方玩家总局数 ≥100
共同同桌局数 ≥100
同桌率 ≥20%
对打率 ≥62%
```

其数据依据为：

- 共同同桌达到100局的玩家对只占全部玩家关系约0.24%；
- 同桌率P95为19.53%、P99为51.02%，30%位于两者之间；
- 对打率P95为72.33%、P99为96.08%，75%略高于P95；
- 该组合同时要求玩家关系强度和下注行为异常，比使用单一指标或 `OR` 条件更适合作为重点审核规则。

推荐风险等级：

```text
观察：
共同同桌局数≥100，同桌率≥20%，对打率≥62%

重点审核：
共同同桌局数≥100，同桌率≥30%，对打率≥75%

极高异常：
共同同桌局数≥300，同桌率≥50%，对打率≥90%
```

该规则应定位为异常关系筛查和人工审核工具，不应单独作为作弊认定或自动处罚依据。
