# 玩家风险等级判定设计

## 1. 目标

为业务提供指定玩家的稳定、可解释风险等级，同时支持：

- 后台展示和人工审核。
- 登录、下注等业务链路的低延迟判断。
- 小时级数据新鲜度。
- 历史判定复盘、规则版本追溯和缓存安全降级。

第一版使用确定性规则评分，不引入机器学习、秒级流处理或请求时动态训练。

## 2. 现状与约束

`wm-trueman-risk` 拥有完整 StarRocks 小时事实：

- `player_pair_stat_hourly`
- `player_round_stat_hourly`
- `dealer_profit_stat_hourly`
- `job_checkpoint`

`wm-trueman-risk-api` 只能读取 API MySQL，不能直接读取 StarRocks、S3 或源 MariaDB。现有 `player_pair_stat` 和 `dealer_profit_stat` 只保存达到阈值的候选关系，不是完整事实。

现有 `GET /v1/risk/players/{playerId}/profile` 用于调查详情。`dealer_profit_stat.risk_score` 和 `risk_level` 仍为 `0 / UNKNOWN` 占位值，不得用于本设计的最终判级。

## 3. 总体架构

```text
StarRocks 完整小时事实
  -> PlayerRiskJob 滚动窗口特征与评分
  -> StarRocks player_risk_assessment_hourly 历史快照
  -> API MySQL player_risk_profile 最新快照
  -> API MySQL player_risk_publish_state 发布状态
  -> Valkey 按玩家缓存
  -> GET /v1/risk/players/{playerId}/assessment
```

### 3.1 项目边界

`wm-trueman-risk` 负责：

- 新增 `--job=player-risk`，仍使用 `com.wm.risk.launcher.JobLauncher`。
- 从完整小时事实计算特征、分数、等级和建议动作。
- 管理 StarRocks 历史快照、API MySQL 最新投影、发布状态、checkpoint 和缓存失效。

`wm-trueman-risk-api` 负责：

- 根据 `player_id` 查询 API MySQL 快照。
- 校验全局发布状态、数据集过期时间和玩家数据状态。
- 执行 HMAC 鉴权、访问审计、限流、缓存和 HTTP 错误语义。
- 不重新计算分数，不修改离线发布的规则结果。

## 4. 数据模型

### 4.1 StarRocks `player_risk_assessment_hourly`

每个已发布评估小时、每个本小时重新计算的玩家一条历史记录。主键粒度：

```text
assessment_date + assessment_hour + player_id
```

字段组：

| 字段 | 语义 |
|---|---|
| `player_id` | 玩家 ID |
| `risk_score` | `0..100` |
| `risk_level` | `LOW / MEDIUM / HIGH / CRITICAL / UNKNOWN` |
| `recommended_action` | `ALLOW / MONITOR / REVIEW / BLOCK` |
| `data_status` | `READY / INSUFFICIENT_SAMPLE` |
| `rule_version` | 首版固定为 `PLAYER_RISK_V1` |
| `signal_codes` | 命中的稳定规则代码集合 |
| `profit_24h`, `valid_bet_24h`, `roi_24h`, `bet_count_24h` | 24 小时盈利特征及规则样本数 |
| `profit_7d`, `valid_bet_7d`, `roi_7d` | 7 天盈利特征 |
| `abnormal_relation_count_7d` | 7 天异常荷官、游戏关系数 |
| `suspicious_pair_count_7d` | 7 天候选同桌玩家数 |
| `max_same_rate_7d` | 7 天最大同桌率 |
| `max_same_round_count_7d` | 7 天最大共同回合数 |
| `signal_day_count_30d` | 30 天中有日级异常的日期数 |
| `cross_evidence_count_7d` | 与候选同桌玩家共享异常荷官和游戏的证据数 |
| `sample_bet_count_30d` | 30 天结算记录数 |
| `sample_valid_bet_30d` | 30 天有效投注，人民币 |
| `sample_round_count_30d` | 30 天去重回合数 |
| `as_of_time` | 该玩家本次重算使用的右开评估截止时间 |
| `created_time`, `update_time` | 审计时间 |

`signal_codes` 在 StarRocks 可使用 JSON 或稳定排序的字符串存储；写入 API MySQL 时统一为 JSON 数组。

### 4.2 API MySQL `player_risk_profile`

每个玩家一条最新快照，主键为 `player_id`。保存 4.1 中除分区键之外的判级和特征字段。新增：

- `(risk_level, risk_score DESC)` 索引，支持后续人工审核列表。
- `(as_of_time)` 索引，支持新鲜度审计。

历史补数只有在 `as_of_time` 不早于当前 API 快照时才能覆盖该玩家，避免旧时间回放倒退线上结果。

### 4.3 API MySQL `player_risk_publish_state`

单行数据集发布状态，固定主键 `dataset_name = PLAYER_RISK`：

| 字段 | 语义 |
|---|---|
| `dataset_name` | `PLAYER_RISK` |
| `as_of_time` | 最后完整发布截止时间 |
| `expires_at` | 数据集过期时间 |
| `rule_version` | 当前规则版本 |
| `publish_status` | 成功发布时为 `READY` |
| `run_id` | 离线任务运行标识 |
| `update_time` | 发布时间 |

该表使 API 在玩家快照不存在时，能区分“全局上游延迟”和“当前玩家无数据”。

API 使用全局 `player_risk_publish_state.expires_at` 判断整个数据管道是否过期，不按玩家行的 `as_of_time` 判断过期。只要受影响键算法证明该玩家在新窗口中没有任何特征进入或退出，之前的评分结果在新的全局截止时间下仍然有效。

## 5. 窗口与特征口径

所有窗口均为基于 `as_of_time` 的左闭右开滚动窗口：

```text
24h: [as_of_time - 24 hours, as_of_time)
7d:  [as_of_time - 7 days, as_of_time)
30d: [as_of_time - 30 days, as_of_time)
```

### 5.1 盈利特征

来源 `dealer_profit_stat_hourly`，金额已通过汇率换算为人民币。

- 玩家总体 `profit = SUM(profit)`。
- 玩家总体 `valid_bet = SUM(valid_bet)`。
- `roi = profit / valid_bet`；`valid_bet <= 0` 时 ROI 为 0，不触发 ROI 规则。
- 7 天盈利关系先按 `(dealer_id, game_id, player_id)` 聚合，再套用候选规则。

7 天盈利候选规则：

```sql
(bet_count >= 20
 AND valid_bet >= 1000
 AND profit > 0
 AND player_roi >= 0.2)
OR profit >= 10000
```

### 5.2 同桌特征

共同回合来源 `player_pair_stat_hourly`，玩家回合分母来源 `player_round_stat_hourly`。每个窗口重新计算：

```text
same_rate = same_round_count / LEAST(player_a_rounds, player_b_rounds)
```

分母小于等于 0 时 `same_rate = 0`。玩家对在窗口内满足以下条件时计为候选同桌关系：

```sql
(same_round_count >= 3
 AND LEAST(player_a_rounds, player_b_rounds) >= 5
 AND same_rate >= 0.3)
OR same_round_count >= 10
```

### 5.3 30 天持续性

按业务时区 `Asia/Shanghai` 聚合日级事实。某日出现以下任一情况即计为一个信号日：

- 存在一组满足 5.1 候选规则的荷官、游戏盈利关系。
- 存在一组满足 5.2 候选规则的玩家对。

`signal_day_count_30d` 为不同信号日数，不按同一日的多条关系重复计数。

### 5.4 交叉证据

对玩家的 7 天候选同桌关系，检查玩家与关联玩家是否在同一 `(dealer_id, game_id)` 下同时满足 5.1 的 7 天盈利候选规则。每个唯一的：

```text
related_player_id + dealer_id + game_id
```

计为一条交叉证据。交叉规则只加分一次，不按证据条数累加 25 分。

## 6. 样本门禁

30 天内满足以下任一条件视为样本充足：

```text
sample_round_count_30d >= 5
```

或：

```text
sample_bet_count_30d >= 20 AND sample_valid_bet_30d >= 1000
```

样本不足时：

```text
risk_score = 0
risk_level = UNKNOWN
recommended_action = REVIEW
data_status = INSUFFICIENT_SAMPLE
signal_codes = ["INSUFFICIENT_SAMPLE"]
```

样本充足且没有风险信号时才能返回 `LOW / ALLOW`。

## 7. `PLAYER_RISK_V1` 评分

| 规则代码 | 条件 | 分值 |
|---|---|---:|
| `PROFIT_SURGE_24H` | 24 小时 `profit >= 5000`，或 `bet_count >= 20 AND valid_bet >= 1000 AND roi >= 0.3` | 10 |
| `PROFIT_ANOMALY_7D` | 至少一组 7 天荷官、游戏盈利关系满足 5.1 | 15 |
| `PROFIT_RELATION_SPREAD_7D` | `abnormal_relation_count_7d >= 2` | 10 |
| `PAIR_ANOMALY_7D` | 至少一组 7 天玩家对满足 5.2 | 15 |
| `STRONG_PAIR_7D` | 至少一组 `same_rate >= 0.6 AND same_round_count >= 10` | 10 |
| `PERSISTENT_SIGNAL_30D` | `signal_day_count_30d >= 3` | 15 |
| `SHARED_DEALER_GAME_EVIDENCE` | `cross_evidence_count_7d >= 1` | 25 |

符合样本门禁时：

```text
risk_score = LEAST(100, SUM(matched_rule_points))
```

等级和建议动作：

| 条件 | 等级 | 建议动作 |
|---|---|---|
| 数据不可信或样本不足 | `UNKNOWN` | `REVIEW` |
| `0..14` | `LOW` | `ALLOW` |
| `15..39` | `MEDIUM` | `MONITOR` |
| `40..69` | `HIGH` | `REVIEW` |
| `70..100` | `CRITICAL` | `BLOCK` |

分数、等级和动作由离线任务同时生成，API 不单独推导动作。

## 8. 受影响玩家与滚动刷新

每处理一个新的整点截止时间，受影响玩家为以下集合的并集：

- 新进入当前小时的 `player_round_stat_hourly.player_id`。
- 新进入当前小时的 `dealer_profit_stat_hourly.player_id`。
- 新进入当前小时的 `player_pair_stat_hourly.player_a/player_b`。
- 分别在 24 小时、7 天、30 天窗口左边界退出的上述玩家。
- 上述直接受影响玩家在 7 天候选同桌关系中的一跳关联玩家。该传播用于覆盖某个玩家盈利关系变化后，其同桌玩家交叉证据同步变化的情况。

对受影响玩家重读最近 30 天完整小时事实，不对 MySQL 快照执行累加写。这保证无新活动但旧信号退出窗口的玩家也会降级，也保证盈利信号变化能传播到交叉证据依赖的玩家。

每日执行一次最新截止时间的全量校准，修复漏刷新、规则调整或异常中断造成的偏差。

## 9. 调度、发布与 checkpoint

新增 DolphinScheduler 工作流：

```text
wm-risk-player-assessment-hourly
```

逻辑依赖：

```text
wm-risk-player-pair-hourly ----\
                                -> wm-risk-player-assessment-hourly
wm-risk-dealer-profit-hourly --/
```

运行前必须再校验 `player-pair` 和 `dealer-profit` checkpoint 均达到 `END_TIME`。调度依赖用于减少无效启动，checkpoint 校验是数据正确性的硬门禁。

单小时发布顺序：

1. 校验上游 checkpoint 和规则配置。
2. 构建受影响玩家并计算快照。
3. 幂等覆盖 StarRocks `player_risk_assessment_hourly` 目标小时。
4. upsert API MySQL `player_risk_profile`。
5. 按受影响 `player_id` 清理 `risk-player-assessment` 缓存。
6. 更新 `player_risk_publish_state`。
7. 推进 `player-risk` checkpoint 到 `END_TIME`。

任一步失败均不推进 checkpoint。MySQL upsert、StarRocks 小时覆盖和缓存失效均允许幂等重跑。发布状态在玩家快照完成后才更新，防止 API 将部分发布认为完整数据集。

`RERUN=true` 不读写 checkpoint。历史评估回放需要在第一个评估截止时间之前准备至少 30 天的小时事实。

## 10. API 契约

### 10.1 端点

```http
GET /v1/risk/players/{playerId}/assessment
```

继续使用现有 `X-Api-Key` 和 HMAC-SHA256-V1 签名体系。`playerId` 必须为正整数。

### 10.2 成功响应核心字段

```json
{
  "playerId": 1001,
  "riskScore": 55,
  "riskLevel": "HIGH",
  "recommendedAction": "REVIEW",
  "dataStatus": "READY",
  "ruleVersion": "PLAYER_RISK_V1",
  "asOfTime": "2026-07-19 15:00:00",
  "calculatedAt": "2026-07-19 15:06:12",
  "expiresAt": "2026-07-19 17:00:00",
  "signalCodes": [
    "PROFIT_ANOMALY_7D",
    "PAIR_ANOMALY_7D",
    "SHARED_DEALER_GAME_EVIDENCE"
  ],
  "metrics": {
    "profit24h": 6800.0000,
    "validBet24h": 12000.0000,
    "roi24h": 0.5667,
    "betCount24h": 36,
    "profit7d": 15000.0000,
    "validBet7d": 36000.0000,
    "roi7d": 0.4167,
    "abnormalRelationCount7d": 1,
    "suspiciousPairCount7d": 2,
    "maxSameRate7d": 0.68,
    "maxSameRoundCount7d": 14,
    "signalDayCount30d": 4,
    "crossEvidenceCount7d": 1,
    "sampleBetCount30d": 180,
    "sampleValidBet30d": 52000.0000,
    "sampleRoundCount30d": 120
  }

```

`asOfTime` 和 `expiresAt` 来自全局发布状态。`calculatedAt` 表示该玩家最后一次因特征变化而重算的时间，不单独决定数据是否过期。

### 10.3 `dataStatus` 与 HTTP 语义

| 场景 | HTTP | `dataStatus` | 等级/动作 |
|---|---:|---|---|
| 数据集已发布且快照有效 | 200 | `READY` | 使用离线结果 |
| 样本不足 | 200 | `INSUFFICIENT_SAMPLE` | `UNKNOWN / REVIEW` |
| 数据集新鲜但玩家不存在 | 200 | `NO_DATA` | `UNKNOWN / REVIEW` |
| 全局发布状态超过两小时 | 200 | `STALE` | `UNKNOWN / REVIEW` |
| `playerId <= 0` | 400 | 无 | 参数错误 |
| API MySQL 不可用 | 503 | 无 | 调用方执行 `REVIEW` |

`UNKNOWN` 是明确的业务结果，不用 404 表示。数据库故障不能伪装成 `UNKNOWN`，否则无法区分“真实无数据”与“系统不可用”。

## 11. 缓存与一致性

新增缓存名：

```text
risk-player-assessment
risk-player-publish-state
```

- 玩家快照 key 为 `playerId`，TTL 为 5 分钟。
- 全局发布状态 key 固定为 `PLAYER_RISK`，TTL 不超过 30 秒。
- 缓存内保存数据库快照，服务层每次响应前仍校验全局发布状态和其 `expires_at`。
- 如果玩家行的 `as_of_time` 晚于全局发布状态，说明正在部分发布或上次发布未完成；API 返回 `STALE / UNKNOWN / REVIEW`，不提前暴露未发布结果。
- Valkey 读写失败时回源 API MySQL，不改变判级。
- 小时增量发布先按受影响玩家失效，再发布新的全局状态并失效发布状态缓存。全量校准和规则版本发布清空两个缓存。
- `RiskCacheNames.ALL` 和缓存管理接口必须包含新缓存。

## 12. 规则配置与版本

规则阈值由 `wm-trueman-risk` 的 PureConfig 生产配置加载，通过 Livy JSON 注入 driver 和 executor。同一 `rule_version` 下的阈值不允许静默修改。

任何影响分数或等级的变更必须：

1. 生成新 `rule_version`。
2. 用历史数据回放。
3. 输出等级分布、规则命中分布、升降级人数和抽样证据。
4. 获得业务确认。
5. 全量重算最新快照并发布。

API 只透传 `rule_version`，不在请求时热更新评分阈值。

## 13. 可观测性

每次离线运行记录：

- `as_of_time`、`run_id`、`rule_version`和耗时。
- 受影响玩家数、写入历史数、MySQL upsert 数和缓存失效数。
- 各 `risk_level` 人数和比例。
- 各 `signal_code` 命中人数。
- 相对上一小时升级、降级、进入 `UNKNOWN` 的人数。
- 两个上游 checkpoint 与本任务 checkpoint 的延迟。

告警条件：

- 任一上游 checkpoint 延迟超过两小时。
- `player-risk` checkpoint 延迟超过两小时。
- 发布状态过期。
- 某个等级比例较近 7 天同时段基线显著偏离。
- MySQL upsert、缓存失效或 checkpoint 推进失败。

## 14. 测试和验收

### 14.1 `wm-trueman-risk`

- 每条规则阈值的下界、等值和上界测试。
- 总分封顶为 100，分数到五级语义的边界测试。
- `valid_bet <= 0`、样本不足、无信号和交叉证据去重。
- 24 小时、7 天、30 天左闭右开边界进入和退出。
- 受影响玩家包含新增事实和过期事实两类键。
- 同一小时重跑的 StarRocks、MySQL 和分数幂等性。
- MySQL、缓存、发布状态或 checkpoint 失败时 checkpoint 不推进。
- 历史回放不能用旧 `as_of_time` 覆盖 API 最新快照。

### 14.2 `wm-trueman-risk-api`

- `READY`、`INSUFFICIENT_SAMPLE`、`NO_DATA`、`STALE` 响应。
- 全局发布状态过期优先于玩家快照结果，必须降级为 `UNKNOWN / REVIEW`。
- `playerId <= 0` 返回 400，MySQL 故障返回 503。
- Valkey 不可用时回源 MySQL。
- 玩家缓存键、按键失效、全量失效和 5 分钟 TTL。
- HMAC 鉴权、重放保护、限流和请求审计沿用现有行为。
- OpenAPI/接口文档与 DTO 字段完全一致。

### 14.3 上线验收

使用至少 30 天历史数据回放，输出：

- 每日和总体五级分布。
- 每条规则命中率和交叉命中率。
- 等级升降转移矩阵。
- `HIGH/CRITICAL` 证据抽样。
- `UNKNOWN` 占比及其 `data_status` 分布。
- 任务耗时、MySQL 写入耗时和 API P95/P99 延迟。

历史回放不自动修改阈值。阈值调整需要新规则版本和业务确认。

## 15. 发布步骤

1. 在 `wm-trueman-risk` 增加配置、DDL、评分纯函数和 Spark 任务。
2. 创建 StarRocks 历史表和 API MySQL 两张新表。
3. 用历史数据生成 `PLAYER_RISK_V1` 校准报告。
4. 获得业务对等级分布和抽样证据的确认。
5. 全量生成最新风险快照，但暂不对业务开放。
6. 在 `wm-trueman-risk-api` 发布查询端点和缓存支持。
7. 先以只展示、不自动拦截的 shadow 模式观察至少 7 天。
8. 按 `MEDIUM -> MONITOR`、`HIGH -> REVIEW`、`CRITICAL -> BLOCK` 顺序分阶段启用处置。

## 16. 非目标

- 不将风险等级解释为最终作弊结论。
- 不在 API 请求中直连 StarRocks 或重算 30 天事实。
- 不复用现有候选投影中的占位 `risk_score/risk_level`。
- 不在第一版引入秒级 Kafka/Flink 链路。
- 不在第一版引入机器学习、自动阈值调参或人工白名单/黑名单覆盖。
