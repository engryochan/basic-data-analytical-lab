解答

这张 player_pair_stat（玩家同桌关系风控候选表），如果放在传统 BI 中，通常只是做几个柱状图和表格；但如果按照顶级电商（Amazon、阿里巴巴、京东）、支付风控（PayPal、Visa）、量化科技（Bloomberg、Databricks）的思路，它应该被视为一张关系特征（Relationship Feature）表，而不是简单的业务明细。

核心目标不是“展示数据”，而是回答四个问题：

  1. 哪些玩家之间存在异常稳定的同桌关系？
  2. 这种关系持续了多久、强度如何？
  3. 异常关系是否正在增长？
  4. 哪些关系需要优先进入人工审核？

因此，在 Superset 中，应将这张表组织成一套由指标层 → 特征层 → 风险层 → 调查层构成的 Dashboard，而不是零散图表。

十四、推荐建立一个增强版 Virtual Dataset

不要直接使用原始表，而是在 SQL Lab 创建一个统一的数据集，例如：

SELECT
    player_a,
    player_b,
    same_round_count,
    player_a_rounds,
    player_b_rounds,
    same_rate,
    first_game_time,
    last_game_time,

    DATEDIFF(last_game_time, first_game_time) AS relationship_days,

    LEAST(player_a_rounds, player_b_rounds) AS min_rounds,

    GREATEST(player_a_rounds, player_b_rounds) AS max_rounds,

    same_round_count /
    NULLIF(LEAST(player_a_rounds, player_b_rounds), 0) AS relation_strength,

    DATEDIFF(CURRENT_DATE, last_game_time) AS active_days,

    (
        0.45 * same_rate
        + 0.35 * (
            same_round_count /
            NULLIF(MAX(same_round_count) OVER (), 0)
        )
        + 0.20 * (
            DATEDIFF(last_game_time, first_game_time) /
            NULLIF(MAX(DATEDIFF(last_game_time, first_game_time)) OVER (), 0)
        )
    ) AS risk_score

FROM player_pair_stat;

有了这个增强版数据集，后续所有图表都直接使用统一的字段，Dashboard 的维护成本会大幅降低。

总体架构建议

针对 player_pair_stat，我建议采用以下分析链路：

全局概览（Big Number） → 分布分析（Histogram、Box Plot） → 风险定位（Scatter、Heatmap） → 排名筛查（Horizontal Bar、Treemap） → 时间演化（Line Chart） → 人工调查（Table）

这种结构与现代电商、支付风控和量化科技平台的数据分析方式一致：既能快速监控整体风险，又能逐步钻取到具体玩家组合，并为后续引入设备、IP、地理位置、盈亏等更多特征预留扩展空间。
