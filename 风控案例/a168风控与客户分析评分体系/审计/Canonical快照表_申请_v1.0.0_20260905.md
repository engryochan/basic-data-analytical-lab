## 一、问题之本质（已实测钉死）

现行导出方式为「分批取数」：

```sql
… ROW_NUMBER() OVER (ORDER BY …) AS audit_rn …
WHERE z.audit_rn > 990000 AND z.audit_rn <= 1000000
```

⛔ **此处之 `WHERE` 位于窗口函数【之外】。** 故它**不能**让引擎「只算一万行」，而是：

> **先把整个结果集排序并编号，再丢弃 99.94%，只留一万行。**

⇒ 每一批都要把 **124,713,543 行注单** 重新去重、重新聚合、重新全局排序一遍。

**实测铁证三条**：

1. 批量由 100,000 改为 10,000（输出小十倍），**仍在同一内存上限撞墙** ——若瓶颈在输出量，此举必然有效；它无效，故瓶颈不在输出量。
2. `#071` 之 `T_true = 18,139,550` ⇒ **1,814 批**；`#133 RK01` 之 `T_true = 6,048,562` ⇒ **605 批**。二者相加 **2,419 次**全量重算。
3. 已导 417 批，仍余 **1,397 批**（仅 `#071` 一件）。

### 请求甲 · 建立 canonical 快照表并灌入一次


其内容即**现行 SQL 之完整输出，一字不改**——包含 `audit_rn`、`batch_id`、`run_id`、`snapshot_sync_time` 及全部业务栏位。

⛔ **不得改动任何一处**：不动六锁、不动指标公式、不动栏位与其顺序、不动 NULL 语义、不动数值精度、**尤其不动 `audit_rn` 之排序键**。本部门可提供逐字之建表与灌入语句。

### 请求乙 · 授予本部门对该二表之 SELECT 权限

其后本部门每批只需：

```sql

```

此时 `audit_rn` 已是**物化的实体列**，非执行中的窗口函数——只需扫一万行，与原先「排序六百万行再取一万」不是一个量级。
