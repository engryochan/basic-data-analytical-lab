# W-66 · `sleep` 探针回执 —— **闹钟，不是墙**

> 时间：2026-08-31 · 证据：五帧 `SELECT sleep(120) AS probe;` 截图（09:23:54 ~ 09:24:27）
> **P4 两件未动一字。** 本报告纯取证与判别。
> **裁定：SQL 无罪。此régime 为一道与负载完全无关的固定时间闸，约 53 秒。**

`SELECT sleep(120) AS probe;` —— **不读任何表、不扫任何行、不申请任何工作内存**。

**五次全部未能跑到 120 秒。** 计时器皆红，结果面板皆空，无任何错误文本。

## 二、把两组摆在一起，答案就出来了

| 组 | n | 均值 | 标准差 | 极小 | 极大 | 极差 | 变异系数 |
|---|---|---|---|---|---|---|---|
| ① `sleep(120)` **空载** | 5 | **53.614 s** | 1.055 | 52.488 | 55.304 | 2.816 | **1.97%** |
| ② 交付件**重查询**（129 件族） | 4 | **52.445 s** | 0.726 | 51.503 | 53.273 | 1.770 | **1.38%** |
| **①＋② 合计** | **9** | **53.095 s** | **1.065** | 51.503 | 55.304 | 3.801 | **2.01%** |

**两组均值只差 1.169 秒。** 粗算 Welch t = 1.964（自由度约 7，0.05 水平需 |t| > 2.36）
⇒ **负载对切断时刻的影响，在现有样本下测不出来。**

这句话的分量在于两组的负载差距有多大：

```
组① ：读 0 行、扫 0 字节、工作内存 ≈ 0
组② ：两遍全扫 ods_a168_bet02（窗口内 1.25 亿行）＋ 全表去重窗 ＋ 六道全局排序
```

**一个什么都不干的查询，和一个要吃掉近 100 GiB 的查询，死在同一秒上。**

⇒ 这不可能是资源问题。**资源墙会随负载移动；这道闸不动。**

## 四、régime 变迁之统一解释（这一轮把前后串起来了）

| 时段 | 现象 | 解释 |
|---|---|---|
| 8/25 ~ 8/30 | 2.675 / 3.716 s 即死，**带 StarRocks 错误框**（`Memory of process exceed limit`），CV **140%** | BE 内存被外部因素**贴死在 99.7375 GiB**，查询一进场就触限 —— **死在 53 秒闸之前**，故看不见闸 |
| 8/31 | 51.5 ~ 55.3 s 才死，**一个字的错误都没有**，CV **2.01%** | 内存压力已缓解，查询得以跑下去 —— **于是撞上了那道一直都在的 53 秒闸** |

⇒ **两道障碍是叠加的，不是替代的。**
过去被内存挡住，看不见闸；如今内存让开了，闸就露出来了。

⇒ **重要推论：内存问题现在无法测量。** 什么都活不过 53 秒，
`T_true` 探针、诊断四门槛全谱、R1 落盘 CTAS ——**统统跑不完**。
**必须先拆闸，才谈得上量内存。** 施工次序须就此调整（见 §六）。

## 五、定位那道闸（三步，由近及远）

### 步骤 1 · 点一下「历史查询」—— 就在界面上，零成本，信息量最大

Superset 的**历史查询**页会记录每条查询的**状态**与**服务端耗时**。

| 历史查询里显示 | 判定 | 闸在哪 |
|---|---|---|
| `sleep(120)` 状态 **success**，耗时 ≈ **120 秒** | 服务端跑完了，**前端先放弃** | **HTTP 层**（Superset web / gunicorn / nginx / LB） |
| 状态 **failed**，带超时类 `ErrorCode` | 服务端自己掐的 | **StarRocks 或 Superset 后端**，去步骤 2 |
| **查不到这几条** | 请求根本没到后端 | **代理 / LB**，去步骤 3 |

⇒ **请先生先点这一下。** 它一步就能把三层分开。

### 步骤 2 · 二分法钉死那个数（每次一条，极轻）

```sql
SELECT sleep(40) AS probe;    -- 预期：通过
SELECT sleep(48) AS probe;
SELECT sleep(52) AS probe;
SELECT sleep(56) AS probe;    -- 预期：被切
SELECT sleep(58) AS probe;
```

找到**最后一个通过**与**第一个被切**之间的界，即为闸值。
经验上会落在 **50 / 55 / 60** 之一（客户端读数比服务端配置略小，
因为计时从点击起算，而服务端从收到请求起算，中间隔着连接池取连接与 FE 解析）。

**顺带的现实收益**：一旦知道界在哪，先生今天就能确定
「**凡预计 < 45 秒者可正常跑**」，不必再盲试。

### 步骤 3 · 按层核对配置（预期会在某处找到 50 ~ 60 秒）

```
Superset  : SQLLAB_TIMEOUT · SUPERSET_WEBSERVER_TIMEOUT
            gunicorn --timeout（缺省 30，Superset 建议 60）
nginx     : proxy_read_timeout · proxy_send_timeout · send_timeout（缺省 60）
云 LB     : idle timeout（AWS ALB 缺省 60）
StarRocks : SHOW GLOBAL VARIABLES LIKE 'query_timeout';
            SHOW SESSION VARIABLES LIKE 'query_timeout';
```

⚠ 后两条**务必与目标查询放进同一次提交** —— 依 **D-1**，会话状态不跨连接池。
总包第 479 行 `SET SESSION query_timeout = 259200;` 若因 D-1 未生效，
实际生效者即是 **global** 值；若有人把它设成 50 或 60，本案当场闭合。

**特别留意 gunicorn `--timeout`**：worker 被 SIGKILL 时，HTTP 连接**不带响应体**就断，
浏览器只见 fetch 失败 —— 这与「计时器变红、结果面板全空、无错误文本」**逐条吻合**。
本人以为此为**当前第一嫌疑**（INFERRED，待步骤 1 证实）。

## 六、今天就能用的两条绕行（不改一行 SQL）

### 绕行 A · 绕开 Superset 与 HTTP 那一层，用 MySQL 客户端直连 FE

```bash
mysql -h <FE_HOST> -P 9030 -u <user> -p \
      --default-character-set=utf8 \
      -e "SELECT sleep(120) AS probe;"
```

- **若此路跑满 120 秒** ⇒ 闸在 HTTP 层，与 StarRocks 无关 —— **诊断闭合，且路已通**。
  其后 129 件取数改走此路（可 `-e "…" > out.tsv` 直接落文件），**今天即可恢复作业**。
- **若此路同样 ~53 秒被切** ⇒ 闸在 StarRocks 或网络层，回步骤 2/3。

这一条**既是判别，又是解药**，性价比最高，建议与步骤 1 并行做。

### 绕行 B · 把 Superset 切到异步（Celery）模式

异步查询在后台 worker 里跑，不受 web 请求超时约束。
须运维配置 Celery broker 与 `RESULTS_BACKEND`，非当场可成，列为中期方案。

## 七、施工次序须重排（这是本轮最要紧的一句）

原先的次序是「先量 BE 内存 → 再谈落盘」。**现在要倒过来：**

```
  ①  拆掉 53 秒闸（步骤 1~3 ／ 绕行 A）
          ↓   —— 在此之前，任何超过 53 秒的东西都测不了
  ②  重新量 BE 内存（SHOW BACKENDS / dmesg / mem_tracker）
          ↓
  ③  跑 T_true 与诊断四门槛全谱（此前一直跑不完）
          ↓
  ④  R1 落盘一次、取多次（CTAS 本身也远超 53 秒，必须先有 ①）
          ↓
  ⑤  D-10 时间血统 · D-12 上游确定性 · D-14 决策层坍缩（须先生逐案裁定）
```

⚠ **在 ① 未成之前，不要再改一行 SQL 去「优化性能」** ——
现在无论把 SQL 优化到多快，只要超过 53 秒就一样死；
而只要低于 53 秒，不优化也能过。**优化与否，此刻不影响结果。**

## 八、一句话

**`SELECT sleep(120)` 什么都不读、什么都不扫、一个字节内存都不要，
照样在 53 秒被掐死 —— 五次，53.614 ± 1.055 秒。
它和那些要吃 100 GiB 的重查询，死在同一秒上，两组均值只差 1.169 秒，测不出差别。
所以：这不是墙，是闹钟；SQL 无罪，P4 一个字都不用改。
先点一下「历史查询」看 `sleep(120)` 服务端是否跑满了 120 秒 ——
再拿 `mysql` 客户端直连 FE 跑一次同样的探针。
这两下，一下定位、一下解套。**
