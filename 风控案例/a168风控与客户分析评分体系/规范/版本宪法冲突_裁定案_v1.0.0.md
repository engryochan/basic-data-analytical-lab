## 一、冲突之精确陈述

`版本编号纪律 v1.0.0` 内并存两组条文，二者在同一版本串上给出**互斥指令**。

### 甲组 · 计数条文

> 三段式 `MAJOR.MINOR.PATCH`，**每段满 999 方晋一级，禁跳级**。

依此，`v11.0.1` 之后只能 `v11.0.2`、`v11.0.3` …… 至 `v11.0.999`，方得进 `v11.1.0`。
**晋级由计数决定，与改动性质无关。**

### 乙组 · 级差判据

| 级 | 硬判据 |
|:--|:--|
| PATCH | **纯代码 MD5 不变** |
| MINOR | 代码 MD5 变，且 `schema_diff` **为空集** |
| MAJOR | `schema_diff` **非空集** |

**兜底铁律**：凡下游三档 `must=` 须随之改动者，无论多小，**一律 MAJOR**。

依此，**晋级由改动性质决定，与计数无关**。

### 二者何以互斥

设某次改动 `schema_diff ≠ ∅`：

- **乙组判为 MAJOR** → 应发 `v12.0.0`；
- **甲组禁其发生** → `PATCH` 段才走到 2，尚差 997 步；`MINOR` 段亦须再走 999 步。

$$\text{欲循甲组抵达 MAJOR，须先发布 } 999 \times 999 \approx 9.98 \times 10^5 \text{ 版}$$

**同一次改动，两条现行条文给出不可同时满足的指令。** 此即冲突之实。

### 冲突之根源（非条文之误，乃设计之限）

一个三段式版本串被要求同时承载**两件正交之事**：

| 事 | 性质 | 要求 |
|:--|:--|:--|
| **发布次序** | 单调计数 | 逐一递增、不得跳号、可稽核发布历次 |
| **契约兼容性** | 语义分级 | 下游据以判「要不要跟着改」 |

**单一字符串无法同时无矛盾地承载二者。** 语义化版本（SemVer）舍弃了「不跳号」；
纯序号制（build number）舍弃了「兼容性语义」。本纪律二者兼取，故必生冲突。

## 二、三条出路及其后果

### 方案甲 · 取计数，废语义

版本串纯表发布次序，`999` 进位维持。

**须一并废止**：级差判据表、兜底铁律、`schema_diff` 判定。

| 后果 | 说明 |
|:--|:--|
| ✅ 得 | 「禁跳级」得以严格执行，发布历次可完整稽核 |
| ❌ 失 | **下游无从由版号判「要不要跟着改」** |
| ❌ 失 | `v11.0.2` 与 `v12.0.0` 之间不再有兼容性含义；`must=` 之同步须另立机制 |
| ⚠ 险 | 「`v11.0.2` 偷偷改 schema」将**无条文可拦**——裁示第八节所忧者正是此 |

### 方案乙 · 取语义，废计数

「满 999 方晋一级」改为「每段容量上限 999」，晋级由改动性质定。

**须一并修订**：「满 999 方晋一级」之文字。

| 后果 | 说明 |
|:--|:--|
| ✅ 得 | 级差判据、兜底铁律、`schema_diff` 全数存活 |
| ✅ 得 | 下游据版号即知是否须同步 |
| ❌ 失 | 版号不再连续，无从由版号稽核发布历次 |
| ⚠ 险 | 恰是本项目此前所患——`v10 → v11` 之间发生过什么，版号说不出来 |

### 方案丙 · **双标识分离**（本册所荐）

**承认二者正交，各给一个标识，不再强塞进同一串。**

```
发布序号  REL-0001, REL-0002, …   单调递增、逐一不跳、满 9999 进位
契约代    C1, C2, C3, …           仅当 schema_diff ≠ ∅ 时递增
```

档名并列二者，例如：

```
a168_取数与核验_SQL总包_REL-0003_C1.sql
```

**判级规则**（乙组判据原样保留，只是作用于「契约代」而非版本串）：

| 改动性质 | 发布序号 | 契约代 | 下游 `must=` |
|:--|:--|:--|:--|
| 纯代码 MD5 不变 | +1 | 不动 | 不动 |
| 代码变、`schema_diff` 空集 | +1 | 不动 | 不动 |
| **`schema_diff` 非空集** | +1 | **+1** | **须同步** |

| 后果 | 说明 |
|:--|:--|
| ✅ 得 | **两条要求同时满足**——序号不跳、语义仍在 |
| ✅ 得 | 甲组「禁跳级」与乙组级差判据**皆无须废止**，只是各归其位 |
| ✅ 得 | 「`REL-0003` 偷改 schema」不可能——改了 schema，`C` 必随之变，档名即露 |
| ❌ 代价 | 须**一次性重排既有版号**，或立等价表将旧号映射至新制 |
| ❌ 代价 | 纪律须实质修订，非勘误 |

**等价映射（若采丙案，须同批冻结）**：

| 旧号 | 发布序号 | 契约代 |
|:--|:--|:--|
| `v10`（≡ `v10.0.0`） | `REL-0001` | `C1` |
| `v11.0.0` | `REL-0002` | `C1` |
| **`v11.0.1`（现 canonical）** | **`REL-0003`** | **`C1`** |

三者 `schema_diff` 皆空集，故同属 `C1`——与既有认知一致（v11 系列系注释斧正，代码零改动）。

## 三、一处**必须同时裁定**的自锁悖论

**「满 999 方晋一级」若适用于纪律档自身，则该纪律不可修订。**

- 修订其条文 → 属「改既有定义之语义」→ 依文档类级差判据为 MAJOR → 应发 `v2.0.0`；
- 而「满 999」禁其发生 → 须先发 `v1.0.999`、再 `v1.999.999`。

**结果：纪律把自己锁死，任何修订皆不合法——包括修订这条锁本身。**

故无论采何方案，须同批裁定一条**元规则**：

> **`版本编号纪律` 自身之版号，不受其所辖之进位条文约束。**
> 理由：规则不能是自己的对象——否则修订之路径由被修订之规则决定，逻辑上不封闭。

此条与「历史上曾这样走过 ≠ 现在有权这样走」并列，同属**元层**条文。

## 四、无论采何方案，皆须同批锁定之三条

**其一 · 版级由契约影响定，不由改动量定**（承裁示第九节）。

> **「代码改了多少行」不决定版级；「对 canonical contract 是否产生结构性影响」才决定。**

凡下列任一发生不兼容变化，**PATCH 禁止**：

```
registry schema ／ 实体定义 ／ 字段结构 ／ topology contract ／ 交付件 schema
```

**其二 · 版号之变更须留六元组** —— 文件名 ＋ 行数 ＋ 字节 ＋ MD5 ＋ 换行符 ＋ 编码，缺一不可。

**其三 · 旧版一律 `_superseded` 存档，永不删除。**

## 五、本册之建议（**仅为建议，裁示权在您**）

**荐方案丙**，理由三：

1. **它是唯一不须废止任何既有判据的方案。** 甲案废语义、乙案废计数，丙案两存。
2. **它精准封死裁示第八节所忧之漏**——「`v11.0.2` 偷偷改 schema」在丙案下**档名即自曝**，
   因为 `C` 不变而 `schema_diff` 非空，二者对不上，一查即现。
3. **代价可控**：现行仅三个历史版号（`v10` ／ `v11.0.0` ／ `v11.0.1`），且三者同属 `C1`，
   等价映射一次冻结即可，无须回溯改档名（旧档保留原名，另立映射表）。

**但须诚实说明丙案之代价**：它不是勘误，是**实质修订**；须依前节元规则处理其自身版号；
且此后一切引用须同报二值（`REL-xxxx` ＋ `Cx`），书写成本略增。
