# 经济结果层 · 粒度对齐规格 v1.0.0

**日期**：2026-08-23　**置放**：`规范/`　**性质**：口径规格（§ECON 之 STEP 5 填实）
**缘起**：业务侧问「`R02_same_table.csv` 尚无 `roi`／`avg`，是否 v12 才加？异常 IP 是否也要加？」

---

## 一、先答版级：按现行纪律为 MAJOR，但纪律本身宜先修一处

### 一之一 · 现行判据之结论

`版本编号纪律 v1.0.0` 之 MINOR 判据写作「`schema_diff` 为空集（**既有交付件之表头一列不增不减不改名**）」。给 `R02_same_table.csv` 增列，`schema_diff` 即非空 → **MAJOR（`v12.0.0` 之后）**。

### 一之二 · 但此判据可能过严（提请裁示）

「增列」与「改名／删列／改义」之破坏力**不同量级**：

| 改动 | 下游影响 | 现行判级 | 建议判级 |
|:--|:--|:--:|:--:|
| **增列**（只增不改不删） | `must=` 若为**子集断言**则完全兼容 | MAJOR | **MINOR** |
| 改列名／删列／改列义 | 必破契约 | MAJOR | MAJOR |

**前置事实待查（可数分钟内查明）**：下游三档之 `must=` 究系**子集断言**（只验必需列在位）抑或**全等断言**（列集须逐字相同）？

- 子集断言 → 增列向后兼容 → 宜判 MINOR；
- 全等断言 → 增列即破契约 → 维持 MAJOR。

**在查明之前，一律按 MAJOR 处理**（取严）。查明后若采纳修订，`版本编号纪律` 自身升 `v1.1.0`（其判据实质变更，非 PATCH）。

## 二、真正的技术障碍不是版号，是**粒度错配**

`§ECON` 第四节之指标字典登记 `grain = member`。而各交付件之粒度**并不相同**：

| 交付件 | T 类 | **粒度** | 直接套 member 级 `roi` 之后果 |
|:--|:--|:--|:--|
| `R01_late_shoe.csv` | T-03 | **会员** | 无碍 |
| `R02_same_table.csv` | T-01 | **会员对** `(uid1, uid2)` | ❌ 「这一对的 ROI」无定义——是谁的 ROI？ |
| `C01_ip_chain.csv`／`I_ip_agg.csv` | T-06 | **IP** ／ 会员×IP | ❌ 一个 IP 之 ROI 系其名下众会员之混合，与个体风险无对应 |
| `R03_player_dealer.csv` | T-02 | **玩家×荷官** | ❌ 同上 |

**铁律**：**经济指标之粒度须与交付件之粒度对齐**；跨粒度直接套用即串线。故不能一句「所有表都加 `roi`／`avg`」了事——须逐粒度另立指标集。

## 三、逐粒度指标规格

### 三之一 · 会员级（`R01` 之属）

沿用 `经济指标字典 v1.0.0` 第二节，不赘。

### 三之二 · **会员对级**（`R02_same_table.csv` · T-01 同桌聚集）

| 指标 | 定义 | 何以有用 |
|:--|:--|:--|
| `stake_pair_sum` | `stake_1 + stake_2` | 该对之总暴露 |
| `ggr_pair_sum` | `−(pnl_1 + pnl_2)` | **平台自这一对身上净赚多少** |
| `hold_pair` | `ggr_pair_sum ÷ stake_pair_sum` | 对级抽水率 |
| `roi_1` ／ `roi_2` | 各自 `pnl ÷ stake` | **须分列，禁平均**——一赢一输被平均即抹去全部信息 |
| **`offset_rate`** | `1 − \|pnl_1 + pnl_2\| ÷ (\|pnl_1\| + \|pnl_2\|)` | **对冲度**：趋近 1 即两员盈亏几乎完全抵销 |

**★ 本节最要紧一条**：对打／同桌聚集之经济指纹**不是高 ROI，是 `hold_pair → 0` 而 `stake_pair_sum` 巨大**。两员方向相反、金额相当时，`pnl_1 + pnl_2 ≈ 0` → 平台**空转流水、抽不到水**；而两员照拿退水。

故：

> **`offset_rate` 高 ＋ `hold_pair` 趋近 0 ＋ `stake_pair_sum` 大** 才是 T-01／T-04／T-05 之经济画像；
> **单看 `roi` 一无所获**——因为对打的设计目标正是让 ROI 趋近 0。

### 三之三 · **IP 级**（`C01_ip_chain.csv` 之属 · T-06 异常 IP 聚集）

| 指标 | 定义 | 判读警告 |
|:--|:--|:--|
| `n_members_eff` | 该 IP 之有效会员数 | 已在册 |
| `stake_ip_sum` | 名下会员本金合计 | 暴露量 |
| `ggr_ip_sum` | `−Σpnl` | 平台自该 IP 净赚 |
| `hold_ip` | `ggr_ip_sum ÷ stake_ip_sum` | 与域均值之差方有意义 |
| `hold_gap_vs_domain` | `hold_ip − hold_域` | **应报此列而非裸 `hold_ip`** |

**★ IP 级之特有陷阱**：一个 IP 可能是网吧、公司出口、运营商 NAT、VPN 出口。**聚合经济量不等于风险**——NAT 之下数百互不相识之会员，其合计 `stake` 天然巨大。故 IP 级经济指标须：

1. **恒与 `n_members_eff` 并报**（人多钱多是算术，不是风险）；
2. **恒报 `hold_gap_vs_domain` 而非裸 `hold_ip`**（偏离域均值才是信号）；
3. `economic_role = PRIORITIZATION`（辅助排序），**不得升 `VALIDATION`**——IP 聚合量不能用来验证任何风险假说。

### 三之四 · 玩家×荷官级（`R03` 之属 · T-02）

同理：须报 `hold_gap_vs_dealer_mean`（该玩家在该荷官台上之抽水率 − 该荷官全台均值），而非裸 `roi`。**裸 `roi` 在此粒度下无判读力。**

## 四、优先级裁定：**增列之前，先补扣项**

`经济指标字典 v1.0.0` 第三节已列：`R01` 之十五列**只到毛利层**，`validbet`（洗码）与 `bet16`（退水）皆不在册。

对照各 T 类之经济机制所在层：

| T 类 | 经济机制落在 | 毛利层指标之效用 |
|:--|:--|:--|
| T-03 尾投 | 毛利（ROI／hold） | ✅ 有效 |
| T-07 技术型玩家 | 毛利 | ✅ 有效 |
| **T-01 同桌聚集** | **扣项（退水）** | ⚠ 近乎无效 |
| **T-04 跨账户对打** | **扣项（退水）** | ⚠ 近乎无效 |
| **T-05 自我对冲／打水** | **扣项（退水）** | ⚠ 近乎无效 |
| **T-08 退水／占成套利** | **扣项（退水＋占成）** | ❌ 完全无效 |
| T-06 异常 IP | 视其名下会员之类型而定 | ◐ 须并报 `n_members_eff` |

**结论**：给 `R02` 增 `roi`／`avg`，在 `bet16` 补齐之前**收益有限**——对打类的钱不在毛利里，在退水里。故**优先级为**：

```
① 名单增列 bet16（退水）与 validbet（洗码）   ← 最高，解锁四类之经济机制
② 各交付件按本册第三节增粒度对齐之经济列       ← 其次
③ 逐员注额分位件（限额档位刻度）              ← 再次
```

**①②③ 皆改表头 → 皆 MAJOR（或按第一节修订后之 MINOR），须与下游三档 `must=` 同步。**

## 五、三条不变之锁

**其一** 经济指标一律 `economic_role = OUTCOME`／`PRIORITIZATION`，**答「造成了什么后果」，不答「为何命中」**。判据仍归各 T 类自身，一字不动。

**其二** `roi > 0` 不是任何一类之判据。零假设下会员 ROI 之期望非 0 而为 `μ₀ = −hold%`；以之出名单行处置者判 **S1 FATAL**。

**其三** 禁裸 `avg`。一律语义化：`stake_avg`／`pnl_avg`／`stake_pair_avg`。
