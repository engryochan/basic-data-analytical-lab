# A168 风控体系：商业盈利操作系统（CPOS）升级方案

## RED TEAM 最终方向

如果目标是打造一套可长期演进、可经受审计、能够支撑商业决策的 A168 风控体系，那么下一阶段最值得投入的工作不是继续增加更多统计模型，而是优先补齐商业盈利闭环。

> **任何框架都不能保证盈利；它只能提高做出更优决策的概率。最终是否提高盈利，仍需依赖真实生产环境中的数据验证。**

---

# 一、商业盈利操作系统（Commercial Profit Operating System，CPOS）

整个系统不再围绕「模型」，而围绕「盈利闭环」。

```text
ODS 原始数据
      │
      ▼
数据质量层（Data Quality）
      │
      ▼
特征工程层（Feature Engineering）
      │
      ▼
能力值层（Capability Scores）
      │
      ▼
领域模型层（Domain Models）
      │
      ▼
Gate 决策层（Decision Gates）
      │
      ▼
Treatment Engine（动作引擎）
      │
      ▼
Outcome Ledger（结果账）
      │
      ▼
Causal Engine（因果验证）
      │
      ▼
Incremental NGR Engine
      │
      ▼
Net Economic Value
      │
      ▼
Continuous Learning
```

---

# 二、所有模型必须回答四个问题

过去很多商业方案容易停留在：

> 模型准确率 95%。

真正应该回答的是：

```text
能发现什么？

能决定什么？

能改变什么？

能赚多少钱？
```

如果第四项暂时回答不了，应明确写：

> **暂不能证明。**

而不能写：

> **一定增加利润。**

---

# 三、能力值必须进入不同 Gate

不要把所有领域压缩为一个综合能力值。

例如：

```text
盈利能力
    ↓
Profitability Gate

异常行为
    ↓
Anomaly Gate

下注能力
    ↓
Betting Gate

生命周期
    ↓
Lifecycle Gate

支付风险
    ↓
Financial Gate
```

不建议简单形成：

```text
综合能力 = 96
```

因为单一综合分无法清楚说明 96 到底代表什么。

> **Multi-Gate ≠ One Composite Score**

---

# 四、Gate 后面必须接动作

评分本身永远不是终点。

正确链条应当是：

```text
Risk Score
    ↓
Gate
    ↓
Treatment
    ↓
Outcome
```

例如：

```text
Sortino < 0.8
    ↓
人工审核

Sortino > 2
    ↓
无需动作

连续异常
    ↓
限制额度

代理风险
    ↓
代理复核
```

---

# 五、所有措施必须计算成本

任何风控措施都不能只计算收益。

至少应考虑：

```text
Review Cost
+
Treatment Cost
+
Churn Cost
+
Technology Cost
+
Operation Cost
```

然后计算：

```text
Incremental NGR
-
所有实施成本
=
Net Economic Value
```

因此：

> **增加 GGR ≠ 真正赚钱。**

# 八、增加反规避 / 对抗层

玩家、代理以及其他参与者可能逐渐学习系统规则。

因此应考虑：

```text
Gaming Detection
Adversarial Detection
Policy Abuse
Threshold Gaming
Rule Circumvention
```

核心原则：

> **模型越公开、规则越固定，就越容易被针对性规避。**

---

# 九、增加商业归因层

所有商业改善都应该区分：

```text
Observed Improvement
        ↓
Correlation
        ↓
Association
        ↓
Prediction
        ↓
Causation
        ↓
Attribution
```

如果没有 Treatment、Control、Outcome、Randomization 或适当准实验，最多只能写：

> **观察到改善。**

不能直接写：

> **本模型带来利润。**

# 十四、最值得投入的四项基础能力

## 1. Treatment Ledger（处置账）

完整记录每一次风控动作：

- 处置对象
- 处置类型
- 处置时间
- 执行人
- 触发原因
- 使用的模型 / Gate
- 处置前状态
- 处置后状态

## 2. Outcome Ledger（结果账）

记录措施实施后的真实业务结果：

- 玩家留存
- 复玩
- 投诉
- GGR
- NGR
- Churn
- 行为变化
- 其他经济结果

## 3. Causal Evaluation（因果评估）

通过：

- A/B Test
- Randomized Control
- 合适的准实验设计

区分：

> **相关**

与：

> **因果。**

## 4. Incremental NGR / Net Economic Value

将：

```text
收益
-
人工成本
-
技术成本
-
处置成本
-
玩家流失成本
-
运营成本
```

纳入统一商业评价。

最终：

```text
Incremental NGR
-
全部相关成本
=
Incremental Net Economic Value
```

只有真实数据持续证明为正，才能逐步确认方案具有可验证的盈利价值。

## RED TEAM 最终原则

> **不能用模型的存在证明盈利。**

> **不能用回测盈利证明生产盈利。**

> **不能用相关性证明因果。**

> **不能用 GGR 增长直接证明 NGR 增长。**

> **不能用 NGR 增长直接证明 Incremental NGR。**

> **不能用 Incremental NGR 忽略实施成本。**

最终必须回到真实生产数据：

```text
Treatment
+
Control
+
Outcome
+
NGR
+
成本
+
Causal Evaluation
=
真实商业证据
```

因此，**实际盈利必须由真实 Treatment / Control / Outcome / NGR 数据产生**；框架本身可以提高验证和决策能力，但不能预先保证盈利。
