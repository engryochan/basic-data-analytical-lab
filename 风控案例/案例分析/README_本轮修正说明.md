## 追加修正（第7轮）：贝叶斯模型改为"快速验证→正式版"两阶段

针对"chains=4/iter=1000/warmup=300/adapt_delta=0.99/max_treedepth=15
跑了十多个小时还没完"的情况，核实了真实数据的模型复杂度：**95位荷官**
(局数从11到2929局不等，极不均衡)、**game_type最多18类**(若走table_id
代理)、Student-t分布、94,468笔样本——荷官局数差距悬殊是阶层贝叶斯模型
典型的"漏斗"病态几何来源，`adapt_delta=0.99`/`max_treedepth=15`大概率
就是之前跑出divergent transition警告后被迫调高的，这两个设置本身就是
在为难采样的模型"买保险"，每一步都算得更小心、更慢。

改为两阶段流程：
1. **快速验证**（`chains=2, iter=400, warmup=200, adapt_delta=0.9,
   max_treedepth=10`，几分钟量级，缓存在`卷房/贝叶斯尤物_快速验证.rds`）
   ——用温和默认设置先摸清楚模型到底难不难采样，印出R-hat、有效样本比例、
   发散转移次数、触及树深上限次数四项诊断指标。
2. **正式版**——依快速验证的诊断结果**自动**决定要不要延用0.99/15：
   若验证阶段一切正常，正式版改用更省时的`adapt_delta=0.9, max_treedepth=10`
   搭配Stan/brms常规建议的`iter=2000, warmup=1000`(4链共4000有效样本)；
   若验证阶段真的出现发散/超树深，正式版才保留0.99/15的保守设置。
   同样缓存在`卷房/贝叶斯尤物.rds`，并保留`bayes_model`这个别名，
   下游代码不用逐处改名。

## 追加修正（第5轮）：30天流失阈值与实际约9.77天的观测窗口不兼容

您实测遇到 `get.grow.event.info(...): no deaths in data!`。已核实：本次
`全局注单表` 的真实时间跨度是 **2026-03-22 07:08 ～ 2026-04-01 01:38，
仅约9.77天**。原代码写死"30天不活跃=流失"，但整份数据总共才9.77天，
任何玩家都不可能"最后一次下注距今超过30天"——`event` 永远全部是0，
randomForestSRC的 `get.grow.event.info()` 发现yvar里一个"死亡/事件"

与本方案其余所有分层判定(风险分层P90/P95/P99、团伙侦测阈值)是同一套
"动态计算、不写死绝对值"原则，而不是给这一处单独开特例。日后拿到覆盖
数月的完整数据后，此判断会自动切回原本30天的绝对定义，不需要改代码。

（顺带一提：这一轮我自己也犯了个方法论错误——曾用"数全文件括号总数"

## 追加修正（第4轮）：RSF因 deposit_count 全NA 被 randomForestSRC 内部丢弃

您实测遇到 `finalizeFormula(...): formula is misspecified, object deposit_count
not found`。已查 randomForestSRC 源码（`utilities.data.R` 的 `is.all.na`/

## 追加修正（第2轮）：brms 默认走 rstan 编译路径导致 Windows 权限报错

您实测渲染时遇到的
```
Compiling Stan program...
Warning in file(con, "r") : 无法打开文件'...cpp.err.txt': Permission denied
错误于file(con, "r"): 无法打开链结
错误于sink(type = "output"): 链结无效
```
是 stan-dev/rstan 仓库里多年反复出现的已知痛点（issue #732/#785/#781/#1082，
时间跨度2018-2023）：rstan 用 `R CMD SHLIB` 编译C++时把编译器报错重定向到
一个临时 `.cpp.err.txt` 文件再读回，一旦该文件因权限/杀毒软件/云同步等原因
读写受阻，rstan 自己的 `sink()` 错误上报机制会跟着崩溃，把真正的编译报错
也一并吞掉。

根因：setup区块费了不少功夫检测/安装/配置 `cmdstanr`，但 `brm()` 调用从未
指定 `backend = "cmdstanr"`——brms默认走的是rstan，前面配置好的cmdstanr
完全没被用上。

修复：
1. setup区块新增 `options(brms.backend = "cmdstanr")` 全局设定
2. `brm()` 调用显式补上 `backend = "cmdstanr"`（双保险）

若切到cmdstanr后仍有类似权限报错，大概率是 `TEMP`/`TMPDIR` 环境变量指到了
OneDrive/Dropbox等云同步文件夹——云同步软件的实时锁定是这类"权限被拒"
报错的常见另一元凶，可检查 `Sys.getenv("TEMP")` 是否落在云同步目录内，
不是的话再考虑重启R session清掉可能残留的锁定临时文件。

## 追加修正（第16轮）：1.7节自动识别函数在全数值表上会崩溃

您实测跑到`自动识别可用模型(日度汇总, ...)`时报
`错误于类别型栏位[sapply(...)]: 类别为'list'的下标无效`。

根因：`sapply()`有个经典陷阱——作用在**长度为0**的输入上时，不会乖乖
回传预期类型的空向量，而是回传`list()`。日度汇总全部栏位都是数值/
日期型，没有任何文字型栏位，"类别型栏位"筛出来自然是空的
(`character(0)`)，对空向量做`sapply(character(0), fn)`就回传了
`list()`，再拿它当下标去筛选，就报"invalid subscript type 'list'"。
全局代理层级表因为本来就有文字栏位(age002等)，"类别型栏位"不是空的，
所以没踩到这个坑——同一份函数代码，遇到不同栏位组成的表，行为不一致。

已把1.7节里两处`sapply()`都换成`vapply()`（明确指定回传类型
`FUN.VALUE = logical(1)`），并对"高基数类别栏位"这步额外加了长度为0
的显式短路判断——vapply()在输入长度为0时会正确回传对应类型的空向量，
不会有这个坑，之后不管表里有没有文字型栏位都能正常跑完。已顺手检查
全文档其余sapply()调用，只有RSF段落里一处(在500棵树固定上限下不会
碰到空输入)，风险低，暂不动它。

这也印证了先前"确保不同观测值都能顺利运行"这条原则的必要性——同一份
函数代码，换一张栏位组成不同的表就崩溃，是需要系统性堵住的一类问题，
不是改一个特例就够。
