## 二、当前卡点：**渲染受制于机器内存，不是代码**

报错位置一路前移，这是最关键的诊断线索：

```
174/221 [arsenal-table]  无法分配bitmap / 无法启动png()装置
  2/243 [setup-python]   OpenBLAS: Memory allocation still failed after 10 retries
```

第二次连 Python 启动都撑不住。**很可能是上次崩溃后残留的进程仍占着内存。**

### 渲染前请依次确认

1. 任务管理器里杀掉残留的 `R.exe` / `rsession.exe` / `python.exe`；
2. 关掉浏览器多余标签页；
3. 开跑后看第一行输出：`ℹ️ 起跑时可用物理内存约 XXXX MB`
   —— **低于 4 GB 就别开始**，会白跑十几分钟再崩。

### 代码侧已经做满的五道闸

| 闸 | 措施 | 位置 |
|---|---|---|
| BLAS 线程 | 锁为 1，且**必须早于 `import numpy`** | `setup-python` 第 139 行 |
| 读入压缩 | ID 列数值化、日期转 Date、计数列整数化 | `fetch()` |
| 用完即释放 | 10 处，每处都在该对象最后一次引用之后 | 全文 `release-*` chunk |
| 建模下采样 | 竞技场 3 万 / 军械库 2 万 / T4 3 万，正样本全留 | 三个 Python 块 |

**若这五道闸之后仍崩，那就是机器内存本身不够**，需要：加内存、或把 Python 章节拆到独立文件单独渲染、或把 `B01_bt_panel.csv`（270 MB）在 SQL 侧少 `SELECT` 几列。

## 六、六条可运行性纪律（每条背后都有一次实测事故）

1. **零占位符** —— Superset 不绑定 `:param`，全文 SQL 一律字面量化。
2. **StarRocks 方言双禁** —— 禁 `LATERAL VIEW EXPLODE`、禁 `EXISTS + 多列 IN`。
3. **片段不落地** —— 引用 `FROM base` 的代码块须前置 E0 主查询。
4. **R 类型判据不能只看 `is.double()`** —— `Date`/`POSIXct` 底层都是 double，
   实测撞过 `Math.Date: floor 对 Date 没有定义`。判据须加 `is.null(attr(v,"class"))`。
5. **行首之外不得出现连续三个反引号** —— Pandoc 认引号、编辑器不认，
   行内出现即让围栏分词器错位，之后所有 chunk 失去 Run Cell 代码透镜。
   需运行时输出围栏用 `strrep` 拼装。
6. **辅助表列名先 `DESC` 再写 join** —— 主表用 `betNN` 代号，辅助表各有各的命名，
   **没有一张叫 `member_id`**。

**另有三条方法论纪律**：缓存不缓存「判定」；参数写死数字＝让缓存说谎；
**静默失效比报错危险**（`hedge_rate` 恒为 0、样本内 AUC、正样本被抽到只剩 1 个——
三次都是不报错却安静产出假数字）。
