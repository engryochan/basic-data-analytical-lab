# 异常IP与尾秒下注风控阈值分析需求文档

## 1. 分析目标



1. 一个IP关联多少个有效账户、盈利账户比例达到多少时，应判定为异常IP。
2. 距离每一把封盘还剩多少秒属于尾端下注，以及玩家至少需要多少尾端下注局数、尾端占比和盈利表现时，应进入风险候选池。

最终需要给出可直接配置到风控平台的阈值，并解释为什么选择该阈值、为什么不选择更宽松或更严格的阈值。

## 2. 分析人员需要回答的问题

### 2.1 异常IP
- “关联20个账户”处于整体分布的什么位置？
- 每个账户至少需要多少订单或物理局，才能被视为该IP的有效关联账户？
- 应使用“账户在该IP下盈利”还是“账户全平台整体盈利”？
- 盈利账户比例使用80%、90%还是100%更合适？
- 不同阈值每天或每个30天窗口会产生多少异常IP、多少关联账户和多少审核工作量？
- 命中IP在不同月份是否持续稳定，还是仅由短期偶然盈利造成？

### 2.2 尾秒下注

- 每一把真实的开始下注时间、封盘时间和下注时长能否准确取得？
- 下注通常集中在第几秒？最后1秒、2秒、3秒和5秒分别覆盖多少订单和玩家？
- 各下注秒段的胜率、盈利、ROI是否存在明显差异？
- “第29秒下注”是否真的表现异常，还是因为大部分正常玩家也集中在第29秒下注？
- 玩家至少需要多少尾秒下注局数，胜率和盈利结果才具有稳定性？
- 尾秒下注占玩家全部参与局数的比例达到多少时才具有行为持续性？
- 尾秒胜率需要达到多少，或者比正常时段胜率高多少个百分点，才适合作为风险条件？
- 玩家是否表现为“正常时段亏损、尾秒时段盈利”，以及这种盈利是否跨月持续？

## 3. 数据范围与基础口径

### 3.1 数据范围

- 数据源：`ods_a168_bet02`，必要时关联每局开始下注和封盘时间表。
- 游戏范围：仅统计 `bet02 = '101'` 的百家乐数据。
- 分析时间：使用可获得的全量历史数据，或者同时按月和滚动30天窗口观察稳定性。
- 时间字段：下注时间使用 `bet08`。
- 玩家ID：`bet05`。
- IP：`ip`。
- 物理局键：`bet03 + bet04 + bet39`。

### 3.2 去重与有效订单

同一 `bet01` 必须按以下顺序保留最新版本：

```text
updatetime DESC
sync_time DESC
dt DESC
```

只统计满足以下条件的最新结算订单：

```text
bet02 = 101
category = 1
UPPER(TRIM(bet38)) = 'N'
bet05 > 0
bet11 > 0
bet08有效
```

IP分析还需要排除：

- 空IP和格式错误IP。
- 已确认的公司出口、测试环境、内部代理或白名单IP。
- 是否排除其他公共网络IP，由数据分析列出影响后交业务确认。

### 3.3 金额和盈利口径

```text
投注金额 = bet13 / bet11
游戏盈利 = (bet14 - bet13) / bet11
返水 = bet16 / bet11
净盈利 = bet17 / bet11
```

- 判断账户整体是否盈利，使用窗口内 `SUM(净盈利) > 0`。
- 分析尾秒下注带来的游戏表现，主要使用不含返水的游戏盈利。
- 净盈利、游戏盈利和返水需要同时输出，避免返水影响对下注优势的判断。

### 3.4 胜率口径

尾秒胜率必须按“玩家物理局”计算，不能按单笔订单计算。

同一玩家在同一物理局的多笔订单先聚合：

```text
局游戏盈利 > 0：胜局
局游戏盈利 < 0：负局
局游戏盈利 = 0：和局
```

```text
胜率 = 胜局数 / (胜局数 + 负局数)
```

和局不进入胜率分母。

## 4. 异常IP阈值分析任务

### 4.1 玩家—IP基础指标

按“统计窗口 + IP + 玩家”计算：

- 玩家在该IP下的去重订单数。
- 玩家在该IP下的去重物理局数。
- 玩家在该IP下的投注金额和净盈利。
- 玩家全平台总订单数和总物理局数。
- 玩家全平台整体净盈利。
- 该IP订单数占玩家全部订单数的比例。

### 4.2 IP汇总指标

按“统计窗口 + IP”计算：

- 原始关联玩家数。
- 有效关联玩家数。
- 盈利玩家数。
- 盈利玩家比例。
- 总订单数、总局数、投注金额和净盈利。
- 关联代理数、荷官数和桌子数。
- 玩家在该IP下的订单占比中位数和P90。

盈利玩家需要同时输出两个版本：

```text
版本A：玩家全平台整体净盈利 > 0
版本B：玩家仅在该IP下净盈利 > 0
```

数据分析需要比较两个版本的命中差异，并推荐正式口径。

### 4.3 分布分析

至少输出：

- 按关联玩家数分组的IP数量、盈利玩家比例和总净盈利。
- 按月份统计各档位IP数量，检查稳定性。
- 关联玩家数最高的前100个IP明细。
- 去除已知公共IP前后的分布差异。

### 4.4 候选阈值组合

至少测试以下候选值：

```text
最小关联玩家数：5、10、20、30、50
玩家在该IP下最小订单数：10、30、50、100
玩家IP订单占比：20%、50%、80%
盈利玩家比例：70%、80%、90%、100%
```

可以先分别分析各参数影响，再选择合理范围进行组合，避免无意义的全量笛卡尔积。

每个候选组合需要输出：

- 命中IP数量。
- 命中玩家数量。
- 预计每个统计周期审核数量。
- 关联总订单数、总投注金额和总净盈利。
- 命中IP的关联玩家数P50、P90和最大值。
- 跨月重复命中率。
- 已知公共IP占比。
- 人工抽样后的可疑率和误报率；没有审核标签时明确标记为“暂不可计算”。

## 5. 尾秒下注阈值分析任务

### 5.1 时间字段可用性检查

分析开始前必须确认：

1. `bet06` 是开始接受下注时间、封盘时间还是正式开牌时间。
2. 是否存在每一物理局的 `open_bet_time` 和 `close_bet_time`。
3. `bet08` 精度是秒还是毫秒。
4. 每局下注时长是否固定30秒。

只有存在可靠的开始下注时间和封盘时间，才能开展正式尾秒阈值分析。

推荐统一指标：

```text
距离封盘秒数 = close_bet_time - bet08
下注进度 = (bet08 - open_bet_time) / (close_bet_time - open_bet_time)
```

如果只能确认每局固定30秒且开始下注时间准确，则可以使用下注后的第几秒；否则不能直接使用“第29秒”。

### 5.2 全体订单秒段分布

至少按以下方式分析：

- 每一秒的订单数、玩家数、局数、投注金额、游戏盈利、胜率和ROI。
- 距离封盘最后1秒、2秒、3秒、5秒分别覆盖的订单和玩家比例。
- 按月份、桌子、房间、荷官、投注类型和 `commission` 分层比较。
- Banker、Player、Tie和边注需要分开分析，不能直接混合胜率。
- 比较尾秒与正常时段的基础胜率和盈利差异。

### 5.3 玩家尾秒指标

按“统计窗口 + 玩家”计算：

- 总参与物理局数。
- 尾秒下注物理局数。
- 尾秒下注局数占比。
- 尾秒胜局、负局、和局及胜率。
- 正常时段胜率。
- 尾秒与正常时段胜率差。
- 尾秒投注金额、游戏盈利、净盈利和ROI。
- 正常时段游戏盈利和ROI。
- 尾秒盈利占玩家全部正向盈利的比例。
- 连续月份尾秒盈利情况。

### 5.4 候选阈值组合

至少测试：

```text
尾端时间范围：封盘前1秒、2秒、3秒、5秒
最小尾秒物理局数：10、20、30、50、100
尾秒下注占比：10%、20%、30%、50%、70%
尾秒胜率：55%、60%、65%、70%
尾秒相对正常胜率提升：5、10、15、20个百分点
```

同时单独测试强特征：

```text
尾秒游戏盈利 > 0
AND 正常时段游戏盈利 <= 0
```

每个合理候选组合需要输出：

- 命中玩家数。
- 预计审核工作量。
- 命中玩家尾秒局数P50、P90。
- 尾秒胜率和正常胜率。
- 胜率差。
- 尾秒投注金额、游戏盈利和ROI。
- 跨月重复命中率。
- 盈利是否由少数极端大额订单主导。

统计置信区间或Z-score可以作为阈值可靠性的分析依据，但不要求作为线上规则条件。线上规则优先使用可解释的实际秒数、局数、比例、胜率和盈利指标。

## 6. 两项规则的组合分析

在两项独立阈值确定后，分析二者交集：

```text
异常IP下尾秒风险玩家数量
异常IP下尾秒风险玩家占比
同一IP成员是否在相同物理局同步尾秒下注
同一IP成员尾秒下注时间差
```

至少比较以下组合门槛：

```text
一个异常IP下尾秒风险玩家数 >= 2、3、5
```

输出不同组合的命中IP数、玩家数、共同尾秒局数、投注金额、游戏盈利和审核工作量，并判断是否需要单独建立高优先级组合规则。

## 7. 阈值选择原则

最终推荐阈值需要同时满足：

1. 指标明显处于总体分布高位，而不是普通用户常见行为。
2. 样本量足够，不能由少量偶然胜局触发。
3. 命中规模符合风控团队实际审核能力。
4. 跨月份表现相对稳定。
5. 不被少量公共IP或极端大额账户主导。
6. 规则条件能够向审核人员清楚解释并追溯原始注单。
7. 宽松一级阈值与严格一级阈值之间存在明显的风险质量或审核量差异。

如果目前没有确认风险标签，最终结论只能定义为“试运行阈值”，不能声称已经得到准确率或召回率最优的生产阈值。
