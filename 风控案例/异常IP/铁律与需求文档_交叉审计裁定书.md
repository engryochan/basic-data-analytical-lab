## 第一部分 · 铁律裁定（逐条，附证据）

```
ods_mariadb_2b.ods_a168_bet02   190,212,574
ods_mariadb_2b.ods_a168_bet01   190,406,429
```

铁律原文缺失中段前缀，属**表述不完整而非错误**。补正后继续生效。

### 铁律② 字段全 varchar 需 CAST

**裁定：完全成立，且比原表述更严重。**

证据：`information_schema.columns` 显示 `ods_a168_bet02` 除 `dt`(date)、`sync_time`(datetime) 外，
**全部 56 列均为 `varchar(65533)`**，含金额、时间、ID。

且实测样本显示存在**空字符串而非 NULL**（`betwalletid`、`ip` 在部分行为空串）。
因此 CAST 前必须 `NULLIF(TRIM(x),'')`，否则空串会静默转 0——
**这在金额列上是致命的**（空串投注额→0，会污染分母）。

铁律②应升级表述为：`CAST(NULLIF(TRIM(x),'') AS ...)`，仅 CAST 不够。

### 铁律④ 过滤 `bet03 != '0'` + 排除 `age022 = 1`

**裁定：前半条成立且被需求文档蕴含；后半条成立且填补了需求文档的缺口。
上一轮我称其「作废」，是错误判断，此处更正。**

#### 前半条 `bet03 != '0'`

实测样本证据：`bet03 = '0'` 的行全部具备以下特征——

```
bet02 = '5031' (Witch Love)   非百家乐
gametype = 3                   电投/第三方
eid = 0                        无荷官
bet39 = 0                      无桌台
ip = ''                        无IP
```

而需求文档 §3.1 限定 `bet02 = '101'`（百家乐）。样本中**所有 `bet02='101'` 的行 `bet03` 均非零**。

**结论**：`bet02='101'` 在逻辑上**蕴含** `bet03<>'0'`，二者不冲突。
铁律④前半条应作为**断言（assertion）保留**，而非删除：

```sql
-- 验证性断言，预期返回 0；若非 0 说明存在百家乐哨兵局，需重新评估
SELECT COUNT(*) FROM ods_mariadb_2b.ods_a168_bet02
WHERE dt >= :from AND dt < :to AND bet02 = '101' AND bet03 = '0';
```

#### 后半条 `age022 = 1`

**证据**：`ods_a168_bet02` 的 56 列中**不存在 `age022`**。
`age` 前缀属代理表族（`ods_a168_agent`、`ods_a168_age_login`、`ods_a168_age_sub_login`）。

**因此铁律④后半条不是错的，而是需要 JOIN 才能执行**——它排除的是**测试代理线下的全部会员**。

而需求文档 §3.2 的有效订单口径**完全没有任何测试账户排除**：

```
bet02=101 / category=1 / bet38='N' / bet05>0 / bet11>0 / bet08有效
```

IP 部分虽提到「排除测试环境IP」，但那是 **IP 级排除，不是账户级**。
**尾秒分析章节（§5）没有任何测试账户过滤。**

**这是需求文档的实质性缺口，铁律④后半条恰好填补它。**
测试账户通常由脚本驱动、下注时刻高度规律，**若不排除，会系统性污染尾秒秒段分布**。

## 第二部分 · 需求文档缺陷清单（七处，附证据与修补）

### 缺陷 1 · 尾秒分析无测试账户排除【严重】

见铁律④裁定。**修补**：join `ods_a168_member.mem019 (is_test)` 与代理测试线，
两级排除后再做秒段分布。

### 缺陷 2 · 全文无分母定义【严重】

见铁律⑤裁定。**修补**：分母 = 窗口内满足有效订单口径的 `COUNT(DISTINCT bet05)`，
所有命中率以此为基数，并在报告首页固定声明。

### 缺陷 3 · `MAX(bet08)` 不能代理封盘时间【致命】

**这是本次审计最重要的发现，也推翻我 v4 里的写法。**

需求文档 §5.1 追问「是否存在每一物理局的 `open_bet_time` 和 `close_bet_time`」，
并规定「只有存在可靠的开始下注时间和封盘时间，才能开展正式尾秒阈值分析」。

我在 v4 中用 `MAX(bet08) OVER (PARTITION BY round_key)` 作为封盘代理。**这是错的。**

实测证据（`bet03 = 114584419`，桌 `bet39 = 3`，同一靴连续六局）：

| 局号 `bet04` | `bet06` 开局 | 实测最早 `bet08` | 实测最晚 `bet08` | 观测跨度 |
|---|---|---|---|---|
| 42 | 12:00:04 | 12:00:05 | 12:00:16 | 12 秒 |
| 43 | 12:00:40 | 12:00:45 | 12:00:52 | 12 秒 |
| 44 | 12:01:14 | 12:01:19 | 12:01:25 | 11 秒 |
| 45 | 12:01:53 | 12:01:59 | 12:02:06 | 13 秒 |
| 46 | 12:02:26 | 12:02:30 | 12:02:38 | 12 秒 |
| 47 | 12:02:59 | 12:03:03 | — | — |

**局间间隔 33–39 秒**（12:00:04→12:00:40→12:01:14→12:01:53→12:02:26→12:02:59），
但**观测下注跨度仅 11–13 秒**。

差额（约 20–26 秒）包含：封盘后发牌、结算、洗牌、下一局开局。

**关键推论**：`MAX(bet08)` 是「最后一个下注的人的时刻」，**不是封盘时刻**。
若某局所有人都在开局后 12 秒内下完，`MAX(bet08)` 会把封盘时刻**低估约 8–13 秒**，
从而把**正常玩家误判为尾秒下注者**。

**这个误差不是随机的，而是与该局人数、注单密度系统性相关**——
人少的局误差大，人多的局误差小。用它做阈值，会得到一个**与桌台热度高度相关的伪信号**。

**修补**：必须定位真实的 `close_bet_time`。候选表（按行数与局数量级匹配度排序）：

| 表 | 行数 | 匹配度评估 |
|---|---|---|
| `ods_a168_game_info` | 11,467,962 | ★★★ 与百家乐局数量级最匹配 |
| `ods_a168_game_log` | 18,007,231 | ★★★ 可能含开/封盘事件流 |
| `ods_a168_game_No` | 152,416 | ★★ 可能是靴级而非局级 |
| `ods_a168_log_realtimebet` | 24,038 | ★ 样本表，但可验证字段语义 |
| `ods_a168_realtimebet` | 4,131 | ★ 同上 |

**若全部不含封盘时间**，则按需求 §5.1 规定，
尾秒章**整章标记为「未实现及原因」**，不得以 `MAX(bet08)` 近似后声称完成。

### 缺陷 4 · §3.4 与 §5.2 在胜率口径上互斥

- §3.4：胜率必须按**玩家物理局**计算，同一玩家同局多注先聚合
- §5.2：Banker / Player / Tie / 边注**必须分开**，不能混合胜率

**矛盾**：一名玩家可能同局既押 Banker 又押 PPair。按局聚合后 `bet09` 被折叠，
无法再分开；若按 `bet09` 分开，则不满足「按物理局计算」。

**修补**：拆为两套互不替代的指标——

| 指标 | 粒度 | 用途 | 对应需求 |
|---|---|---|---|
| 玩家局胜率 | 玩家 × 物理局 | 玩家级尾秒风险判定 | §3.4 / §5.3 |
| 选项绩效 | 订单 × `bet09` | 秒段与投注类型的绩效比较 | §5.2 |

两表并列输出，**明令禁止交叉引用**。

### 缺陷 5 · 净盈利口径会把洗码客误判为盈利账户【严重】

§3.3 规定「判断账户整体是否盈利，使用窗口内 `SUM(净盈利) > 0`」。
而 `净盈利 = bet17/bet11`，实测验证 `bet17 = (bet14−bet13) + bet16`，**含返水**。

**后果**：一名纯靠返水维生的洗码客，游戏盈利为负、返水覆盖亏损后净盈利为正，
会被计入「盈利玩家」，从而**抬高该 IP 的盈利玩家比例**。

洗码客往往集中在同一代理线、共用出口 IP——**这会系统性制造异常 IP 误报**。

**修补**：盈利玩家判定增设第三版本，三版并列：

```
版本A：玩家全平台净盈利 > 0            （文档原定义）
版本B：玩家仅在该IP下净盈利 > 0        （文档原定义）
版本C：玩家游戏盈利 > 0（不含返水）    ★ 本审计新增
```

**版本 C 才是「这些人是否真的赢了庄家」的口径。**
A/B 回答的是「他们钱包是否变多」，二者在洗码场景下结论相反。

### 缺陷 6 · §4.2「关联代理数」未指明层级

`bet18`–`bet22` 对应 LV1–LV5。不同层级的「代理数」含义差异极大：
LV1 可能是总代理（NDV 极低），LV5 是直属代理（NDV 高）。

**修补**：五级全部输出，并以 **LV3** 为主口径（实测样本显示 LV3 区分度最佳），
在报告中说明选择理由。

### 缺陷 7 · 未定义窗口对齐方式

§3.1 要求「按月和滚动30天窗口观察稳定性」，但未规定：

- 滚动窗口的**步长**（每日滚动？每周？）
- 窗口是**半开** `[t, t+30)` 还是闭区间
- 跨月边界如何处理

**修补**：统一采用**半开区间**、**每日滚动**、**窗口右边界为 `as_of`**，
并在每条记录固化 `window_start` / `window_end` / `as_of`，保证可重放。

## 第四部分 · 能力值维度扩展（合并全部可用表）

| 维度 | 数据来源 | 构成指标 |
|---|---|---|
| **资金能力** Capital | `bet02` + `member_dtl` + `tablelimit` + `in_out_m` | 投注规模分位、单注/桌限比、净存款、限额档位 |

| **协同能力** Coordination | `bet02`(IP/LV链) + `employee`(荷官IP) + `mem_login` | 同局共 IP、代理链重合、**荷官 IP 碰撞**、同步时间差 |
| **效率能力** Efficiency | `bet02` | 游戏 ROI（**不含返水**）、胜率相对基准 Lift |
| **持续能力** Persistence | 跨月面板 | 连续盈利月数、跨月重复命中率、活跃密度 |
| **规避能力** Evasion | `mem_login` + `iphistory` + `bet02` | IP 切换频次、局内换 IP、登录/下注 IP 不一致率 |
| **返水依赖** Rebate-Dependency ★新增 | `bet02`(bet15/bet16) | 返水占净盈利比、无返水时是否仍盈利 |

> 前者可能是风险，后者是成本结构问题，两者的处置方式完全不同。
